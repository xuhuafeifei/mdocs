# 知识图谱 — 需求分析

> 一句话：从 mdocs 的「AI 原生知识库 / 人和 Agent 的知识桥梁」定位出发，知识图谱是桥梁的基础设施——AI 自动从文章中提取概念、建立语义关系，让人能快速看懂知识结构，让 Agent 能沿着关系做语义检索。

## 顶层逻辑链（为什么要做图谱，从产品定位出发）

```
mdocs 定位：AI 原生知识库，人和 Agent 的知识桥梁
    │
    ▼
桥梁的核心要求：人和 Agent 都要高效理解和利用知识
    │
    ├── 人的痛点：文档多了乱，新人看不懂全局，找东西靠猜
    ├── Agent 的痛点：只能关键词搜，理解不了知识结构
    │
    ▼
共同解法：把知识之间的关系显性化 —— 知识图谱
    │
    ├── 对人：可视化图谱 = 知识地图，快速建立全局认知
    ├── 对 Agent：结构化关系 = 语义索引，精准理解和检索
    │
    ▼
关键难题：图谱谁来维护？手动维护必死
    │
    ▼
答案：AI 全自动，人零干预
    │
    ├── AI 负责：从文章提取概念 + 归纳上层知识 + 建立关系
    ├── 人负责：只看，不改 —— 降低使用门槛，让图谱自己长出来
    │
    ▼
落地形式：每目录一份 ___graph___.json 隐藏文件 + 图谱页面可视化
```

**结论：知识图谱不是一个"加不加都行"的功能，而是「AI 原生知识库」这个定位的必然产物。**
传统知识库（语雀/Notion/Obsidian）不需要图谱，因为只有人用，人靠脑子自己建图谱。
但 AI 原生知识库不一样——Agent 没有"脑子"可以自己建图谱，你得把图谱给它。同时人也受益——有了图谱，人理解知识的速度也快了。

## 背景

mdocs 作为知识库，文档多了之后"乱"是核心痛点：
- 人进一个新域，不知道从哪看起，文档之间什么关系全靠猜
- Agent 搜索只能关键词匹配，理解不了知识体系的结构
- 目录是按存储组织的，不是按知识逻辑组织的——文档之间的语义关系是隐性的，存在作者脑子里

目前 default 域 160+ 篇文档，横跨多个主题，交叉引用多，新人（和 Agent）很难快速建立全局认知。

## 核心判断（第一性原理）

### 1. 关系比层级重要
图谱的本质是**关联关系**，不是严格的树形结构。概念之间能连就连，连不上就独立存在，不用为了"有层级感"硬凑。

### 2. 知识节点要有厚度
知识不是标签。每个概念节点至少要有一段描述，最好有准确定义——让人看到节点名就知道"这是什么"。没有厚度的节点只是标签云，不是知识图谱。

### 3. AI 全自动，人零干预
让人干活就没动力，图谱就长不出来。接受 70 分的自动图谱 > 追求 90 分但没人维护的空图谱。质量问题靠置信度过滤，不靠人工确认。

### 4. 每个知识都能追溯到原文
概念节点必须有来源（sources），要么直接来自文章，要么来自其他概念的归纳。顺着 sources 一直往下追，最终都能追到具体文章——这是知识可信度的底线。

### 5. 目录层级 ≠ 知识层级
目录是存储结构，知识层级是语义结构，两者解耦。构建顺序按目录自底向上，但知识本身的组织由 AI 根据语义归纳，不被目录束缚。

## 目标

1. **人能快速看懂一个域的知识结构**——打开图谱页看到概念关系网，点节点能看到定义/描述，快速建立全局认知
2. **Agent 能高效利用文档关系**——搜索/问答可以沿着关系网扩展，而不是只靠关键词匹配
3. **用户零额外负担**——正常写文档，AI 自动建图，不需要手动维护或确认
4. **每个概念都有出处**——所有知识都能追溯到原文，可信可验证

## 非目标（本期不做）

- 人工确认/编辑/删除节点或关系（人只看不改）
- 跨目录的上层概念归纳（只做本目录内归纳，父目录只合并不生成新概念）
- 概念级图谱的深层（3 层以上）归纳
- 知识卡片 / 学习路径推荐
- 跨域图谱
- 知识过时检测 / 去重
- Agent 写回图谱
- 行级/段落级精确来源锚点（初版只精确到文章 + 可选标题）

## 核心概念

### 节点（Nodes）

| 类型 | 说明 | 来源 |
|------|------|------|
| `doc` 文档节点 | 一篇 Markdown 文章 | 天然存在，从文件系统来 |
| `concept` 概念节点 | 一个知识概念，有 name + definition/description | AI 从文章提取，或从其他概念归纳 |

概念节点有**知识厚度**：至少有 `description`，优先有 `definition`。不是简单标签。

### 关系（Edges）

语义关系，构成图谱的骨架：

| 类型 | 方向 | 说明 | 初版优先级 |
|------|------|------|-----------|
| `mentions` | doc → concept | 这篇文章提到了这个概念 | P0 |
| `contains` | concept → concept | A 包含 B（B 是 A 的子领域/子概念） | P0 |
| `related_to` | 双向 | 两个概念/文档有语义关联 | P1 |
| `references` | doc → doc | A 文里链接了 / 明确提到了 B 文 | P1 |

初版核心做 `mentions` + `contains`，构成最基础的"文章→概念→上层概念"的层级结构。

### 溯源（Sources）

每个概念节点都有 sources，指向知识的来源：

| 来源类型 | 说明 |
|---------|------|
| `doc` | 直接从某篇文章提取/总结 |
| `concept` | 从其他概念归纳而来 |

sources 是节点的元数据，不是图的边。点节点时展示，用于追溯和可信度背书。

### 构建模型（A1：每目录一份 + 懒聚合）

- 每个目录下有一份 `___graph___.json`，存本目录的图谱数据
- 构建顺序：自底向上（先子目录，后父目录）
- 父目录的图谱 = 本目录文章提取的概念 + 所有子目录图谱的合并（去重）
- 初版父目录只合并不归纳（不生成跨子目录的上层概念）
- 渲染时按需聚合：看哪个目录就聚合哪个目录及其子树

## 验收标准

1. 每个目录下可生成 `___graph___.json` 隐藏文件，不污染用户文档树
2. 图谱页面能以力导向图方式展示概念和文档的关系网络
3. 每个概念节点有名称 + 描述（至少），点节点可查看详情和来源
4. 关系类型至少包含 mentions 和 contains，能形成基本的层级感
5. 父目录视图能正确聚合并展示子目录的所有节点和关系
6. AI 分析一个目录后，概念节点都能追溯到具体文章
7. 性能：打开目录图谱秒级响应（读本地 JSON，不需要 AI 实时分析）

## 本次变更（可读展示 / 分层展开）

> 一句话：不改图谱数据与构建，只改前端呈现——默认顶层骨架 + 按需展开，让人能看懂。

### 背景

全量力导向一次画出所有节点与边（含包含 / 依赖 / 相关），交叉严重、标签截断，人类无法建立全局认知；与验收「人能快速看懂知识结构」冲突。硬排成静态树又有失「关系比层级重要」。

### 目标

- 默认只显示 `contains` 顶层 concept
- 节点可一层层展开；工具栏提供「展开一级 / 展开到二级 / 全部收起」
- 非层级边默认隐藏、可开关叠加；悬停立刻全名；单击进详情

### 非目标

- 不改后端 / `___graph___.json`；不做 ego 邻域、双栏大纲（可后续）

### 验收（增量）

1. 打开目录图谱默认非全图毛线团，可见为顶层骨架
2. 角标可展开/收起分支；三按钮行为符合设计契约
3. 依赖/相关默认不画；开关后仅连可见节点
4. 悬停即时全名；单击详情与展开不打架

## 本次变更（单一焦点：文档 | 图谱）

> 一句话：全局同一时刻只焦点一篇 md 或一个图谱隐藏资源；Ask 引用与焦点一致，二选一。

### 背景

隐藏图谱文件不在树上，无法走旧 `activeDocumentId` 高亮；用户需要「看/生成图谱」时有清晰选中态，并让助手能引用该缓存，又不能和正文选中并存搅乱。

### 目标

- 单一 `AppFocus`：`document` | `graph`
- md → 老树高亮 / 编辑器 / Ask `documentId`
- 图谱 → 独立树高亮 + GraphPage；Ask `graphFileId`
- 禁止把 graph 当正文编辑；get 可读、overwrite 拒绝

### 非目标

- 双焦点；树里画出隐藏文件行；coding 写 graph JSON
