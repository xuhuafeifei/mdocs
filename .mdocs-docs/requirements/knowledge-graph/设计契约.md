# 知识图谱 — 设计契约

> **状态**：草案（2026-08-13 更新）
> 未经「已同意」不得开始写代码。

## 方案摘要

每个目录下新增 `___graph___.json` 隐藏文件，由 AI 自动分析生成：从文章中提取知识节点（doc 节点，带来源），再从知识节点中归纳出概念（concept 节点，不带来源），建立 contains 层级关系。构建按目录自底向上，父目录聚合所有子目录的图谱（只合并，不做跨目录归纳）。前端提供图谱页面，以力导向图可视化呈现，用户可点击节点查看定义/描述和来源。**AI 全自动，人零干预**。

整体架构：

```
┌──────────────────────────────────────────────┐
│  图谱页面（前端）                             │  ← 力导向图可视化 + 节点详情
├──────────────────────────────────────────────┤
│  Graph API（后端）                           │  ← 读 JSON、聚合、触发分析
├──────────────────────────────────────────────┤
│  AI 分析服务（Agent）                        │  ← 提取概念、归纳、建立关系
├──────────────────────────────────────────────┤
│  ___graph___.json（每目录一份，隐藏文件）      │  ← 结构化存储：nodes + edges
└──────────────────────────────────────────────┘
```

## 隐藏文件设计

### 两层结构

知识图谱的隐藏文件分两层：

| 层级 | 文件 | 内容 | 说明 |
|------|------|------|------|
| 文章级 | `__graph__/{documentId}.graph.json` | 单篇文章提取的知识节点（doc 类型） + meta | 知识提取的缓存，用于增量更新 |
| 目录级 | `___graph___.json` | 节点（doc + concept） + 边（完整图谱） | 目录内所有知识的关系网络 |

文章级只有节点（doc 类型，没有边），目录级才有完整的 nodes + edges。doc 节点是目录级的"原材料"，concept 节点是从 doc 节点中进一步归纳出来的。

所有隐藏文件通过 mdocs 文件存储系统读写（与普通文档共用同一套 file-store），不出现在文档树和搜索结果中。

### 文章级隐藏文件

**路径**：`{目录}/__graph__/{documentId}.graph.json`

```json
{
  "version": 1,
  "documentId": "doc-uuid-123",
  "docPath": "auth/recovery-code.md",
  "indexedAt": "2026-08-13T10:00:00Z",
  "meta": {
    "lastIndexedCommitId": "commit-abc123",
    "needSync": false
  },
  "nodes": [
    {
      "id": "doc:recovery-code-intro",
      "type": "doc",
      "label": "恢复码是什么",
      "definition": "恢复码是一串由系统生成的字符序列，用于在丢失访问凭证时恢复访客身份。",
      "description": "基于 SHA-256 哈希生成，一次性使用。用户在设置页生成后需自行保存，换设备或清除缓存时可用于恢复身份。",
      "confidence": 0.9,
      "sources": [
        {
          "type": "doc",
          "documentId": "doc-uuid-123",
          "title": "恢复码",
          "heading": "什么是恢复码"
        }
      ]
    },
    {
      "id": "doc:recovery-code-generation",
      "type": "doc",
      "label": "恢复码的生成方式",
      "description": "系统使用 SHA-256 算法对访客 ID + 时间戳进行哈希，截取前 32 位作为恢复码。",
      "confidence": 0.85,
      "sources": [
        {
          "type": "doc",
          "documentId": "doc-uuid-123",
          "title": "恢复码",
          "heading": "生成规则"
        }
      ]
    }
  ]
}
```

#### 字段说明

| 字段 | 类型 | 说明 |
|------|------|------|
| `version` | number | 文件格式版本，目前 1 |
| `documentId` | string | 对应文档的 id |
| `docPath` | string | 文档相对路径（冗余存储，便于调试和聚合） |
| `indexedAt` | string | 上次索引时间（ISO） |
| `meta.lastIndexedCommitId` | string | 上次索引时文档的 commitId。用于增量判断 |
| `meta.needSync` | boolean | 是否需要重新同步（true 表示文章有变动，需要重算） |
| `nodes` | array | 从这篇文章提取的知识节点列表（都是 `type: "doc"`） |

> 文章级文件中的节点都是 `doc` 类型（从文章直接提取的知识块），每个节点都有 sources 数组，记录它来自哪篇文章的哪个部分。

#### 增量更新判断逻辑

每次构建图谱时，对每篇文章：

1. 读当前文档的 headCommitId
2. 读 `__graph__/{documentId}.graph.json`（如果存在）
3. 若不存在 → needSync = true，需要重新提取
4. 若存在且 `lastIndexedCommitId === headCommitId` → 内容未变，needSync = false，直接复用
5. 若 commit 不同 → needSync = true，重新 AI 提取，更新 meta 和 nodes

> diff 阈值优化（小变化不重算）后续再加，初版 commit 变了就重算。

### 目录级隐藏文件

**路径**：`{目录}/___graph___.json`

```json
    }
  ],
  "edges": [
    { "from": "concept:recovery-code", "to": "doc:recovery-code-intro", "type": "contains", "confidence": 0.9 },
    { "from": "concept:identity-auth", "to": "concept:recovery-code", "type": "contains", "confidence": 0.8 },
    { "from": "concept:identity-auth", "to": "doc:visitor-migration-overview", "type": "contains", "confidence": 0.75 }
  ]

```

### 节点字段说明

所有节点都是**知识节点**，按来源分为两种 type。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | string | 格式 `{type}:{slug}`，全局唯一 |
| `type` | string | `"doc"` 或 `"concept"` |
| `label` | string | 节点名称/标题（显示用） |
| `definition` | string | 准确定义。有则填，可为空 |
| `description` | string | 一段描述。**至少有这个，不能为空** |
| `confidence` | number | AI 置信度 0-1 |
| `sources` | array | **只有 doc 类型有**：来源文章列表。代码填充，AI 不输出 |

> **doc vs concept 的区别**：doc 节点是从**单篇文章**中直接提取的知识块，所以有 sources；concept 节点是从**多个已有节点（doc 或 concept）** 中归纳抽象出来的概念，没有 sources。

### Sources 字段说明

每个 source 对象（目前只有 doc 一种类型）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `type` | string | 固定 `"doc"` |
| `documentId` | string | 来源文档 id |
| `title` | string | 来源文章标题（冗余，便于展示） |
| `heading` | string | 可选，来源文章内的标题锚点 |

### 边字段说明

| 字段 | 类型 | 说明 |
|------|------|------|
| `from` | string | 起点节点 id |
| `to` | string | 终点节点 id |
| `type` | string | 关系类型 |
| `confidence` | number | AI 置信度 0-1 |

### 关系类型定义

| 类型 | 方向 | 说明 | 初版 |
|------|------|------|------|
| `contains` | concept → doc / concept → concept | A 包含 B（A 更抽象/宽泛，B 更具体） | P0 |
| `related_to` | 任意节点 ↔ 任意节点 | 两个节点有语义关联 | P1 |

> contains 的方向：上层 → 下层（抽象 → 具体）。所以 concept 可以包含 doc，也可以包含更具体的 concept。

### 节点命名与去重规则

- 节点 id 由 `{type}:` + label 归一化 slug 组成
- 归一化规则：转小写、去首尾空格、中文/英文数字保留、特殊字符替换为 `-`
- doc 节点 id 中可以包含文章标识（如 `doc:recovery-code-intro`），由 AI 或代码生成时保证唯一性
- concept 节点按 label 去重：同一目录内同名 concept 自动合并，取最高置信度的 definition/description 和 confidence
- 跨目录合并时同理（聚合时处理）

### 文档树中的过滤

以下文件/目录不出现在文档树和搜索结果中：
- `___graph___.json`（目录级图谱文件）
- `__graph__/`（文章级图谱文件目录）
- 与 `desc.md` 同级，属于特殊保留名

## 技术决策记录

### 决策 1：增量 diff 与 AI 输入都用 Markdown，引入 lobe headless

- **状态**：accepted（初版）
- **上下文**：
  - 文章级隐藏文件需要增量判断（变化大才重算概念，小修改跳过）
  - commit blob 和当前文档内容都是 Lexical JSON 格式
  - 直接 diff JSON 字符串无意义（节点 id、format 等元数据噪音大）
  - lobe editor 有 headless 模式，Node.js 可跑，支持 Lexical ↔ Markdown 完整双向转换
- **决策**：
  - 两端 Lexical 都转出为 **Markdown**，再做行级 diff 估算变化比例
  - 引入 **lobe headless** 做 Lexical ↔ Markdown 转换
  - AI 概念提取的输入也用 Markdown（格式信息有助于提取质量）
- **理由**：
  - Markdown 行级 diff 可读、可解释，变化比例估算更准
  - 纯文本 diff 丢失结构信息（改标题和改正文，字符变化差不多但语义重要性不同）
  - AI 提取概念时，Markdown 格式（标题层级、列表、代码块等）能帮助理解文章结构
  - 反正图谱模块也要对接 Agent/AI，多引入 lobe headless 不算额外的架构负担
- **后果**：
  - 后端需要引入 lobe headless 依赖
  - 转换比纯文本提取慢，但增量判断是后台异步的，不影响用户体验
  - 概念的 definition/description 初版仍存纯文本（给人看的摘要不需要格式）

### 决策 2：AI 分析拆为三条独立链路（三次独立调用）

- **状态**：accepted（初版）
- **上下文**：
  - 图谱构建需要 AI 参与的环节有三个：概念提取、上层归纳、关系生成
  - 可以一次调用让 AI 输出全部结果，也可以拆成三次调用
- **决策**：拆为三条独立链路，每次调用只做一件事
  1. **extractConcepts**：文章 → 概念列表
  2. **induceUpperNodes**：下层概念 → 上层概念节点
  3. **generateContainsRelations**：全部概念 → contains 关系列表
- **理由**：
  - 每次任务更聚焦，AI 输出质量更可控
  - 输出结构更简单，出错概率低
  - 方便单独调试和优化 prompt
  - 某条链路失败不影响其他链路（可以重试或降级）
  - 以后扩展其他关系类型（related_to 等），就是新增一条链路
- **后果**：
  - 多两次 API 调用，token 成本略高
  - 每次调用要等结果，总耗时略长
  - 但图谱构建是后台异步的，耗时和成本可以接受

### 决策 3：输出用自然语言 label 关联，不用 id；用 JSON + Zod 校验，失败重试一次

- **状态**：accepted（初版）
- **上下文**：
  - AI 输出关联关系时，可以用 id 关联，也可以用 label（概念名）关联
  - 输出格式可以是纯文本、JSON、XML 等
- **决策**：
  - AI 输出用 **label（中文名）** 关联，不用 id
  - 输出格式强制 **JSON**，用 Zod 做结构化校验
  - 解析/校验失败时，**把错误信息返回给 AI 重试一次**，再失败才抛错
  - JSON 容错：支持 code fence、自动提取最外层 JSON 对象
- **理由**：
  - AI 对自然语言（label）的把握远比对格式规则（slug/id）强，出错率低
  - Zod 校验保证输出结构正确，类型安全
  - 一次重试能解决大部分格式问题，成本不高
- **后果**：
  - 代码里需要做 label → id 的映射转换
  - 存在同名概念冲突风险（初版规模下概率低，冲突时报错或加后缀处理）

## LLM 交互设计

### 总体架构

```
业务层（GraphLLM 接口）
    ↓ 每条链路一个文件
Prompt + 解析封装层
    ↓ 共用
JSON 容错提取 + Zod 校验 + 单轮重试
    ↓
底层 LLMProvider（pi-ai / Anthropic 兼容）
```

底层 Provider 只有一个 `complete(system, user): Promise<string>` 方法，不感知业务。业务层通过 prompt 定义任务，解析封装层负责格式正确性。

### 链路 1：extractDocNodes（从文章提取 doc 节点）

- **触发**：构建单篇文章时
- **输入**：文章 Markdown 全文 + 文档元信息（标题、id）
- **输出**：doc 节点列表（label、definition?、description、confidence、sourceHeading?）
- **Prompt 要点**：
  - 角色：知识提取专家
  - 从文章中提取 3-10 个知识要点，每个要点是一个独立的知识节点
  - 每个节点至少有 description，优先有 definition
  - 标记来源标题（能对应上的话）
  - 只输出 JSON，不要多余文字
- **代码补充**：生成 id（`doc:{slug}`） / type=doc / sources（type=doc，填入 documentId、title、heading）

### 链路 2：induceConceptNodes（从 doc 节点归纳 concept 节点）

- **触发**：构建目录时，汇总完本目录所有 doc 节点后
- **输入**：当前目录范围内所有 doc 节点（label + description）
- **输出**：concept 节点列表（label、description、confidence）
- **Prompt 要点**：
  - 角色：知识归纳专家
  - 从知识节点中归纳出若干上层概念（数量约为总数的 1/3 ~ 1/5）
  - 每个概念是对多个相关知识节点的抽象概括
  - 允许多父（一个 doc 节点可属于多个 concept）
  - 合并不了的可以不归（不强求全覆盖）
  - 只输出 JSON
- **代码补充**：生成 id（`concept:{slug}`） / type=concept；concept 节点没有 sources

### 链路 3：generateContainsRelations（生成 contains 关系）

- **触发**：生成 concept 节点后
- **输入**：全部节点（doc + concept）的 label + description + type
- **输出**：contains 关系列表（fromLabel、toLabel、confidence）
- **Prompt 要点**：
  - 角色：知识图谱关系专家
  - 判断包含关系（A contains B = A 更抽象/宽泛，B 更具体）
  - from = 上层（更抽象），to = 下层（更具体）
  - concept 可以包含 doc，也可以包含更具体的 concept
  - 只输出高置信度的关系，宁缺毋滥
  - 只输出 JSON
- **代码补充**：
  - label → id 转换
  - 生成 GraphEdge（type='contains'）

### 容错与校验

所有链路共用同一套容错策略：

1. **JSON 提取**：去除 ``` 围栏，提取最外层 `{...}`
2. **JSON.parse**：解析失败进入重试
3. **Zod 校验**：字段类型、必填项、数值范围校验，失败进入重试
4. **重试机制**：把错误信息附加到 user prompt 中，让 AI 修正输出，最多重试 1 次
5. **最终失败**：向上抛出异常，由上层决定如何处理

## 统一入口

### 入口设计

图谱构建只有**一个入口**，给定一个路径（文档或目录），为其构建知识图谱：

```typescript
buildKnowledgeGraph(target: string): Promise<GraphResult>
```

### 判断逻辑

```
给定 target：
  1. 判断 target 指向什么：
     ├── 普通 .md 文章 → 构建文章级图谱
     │     （更新 __graph__/{docId}.graph.json，含增量判断）
     ├── ___desc___.md → 当作目录处理
     │     （目录描述文件语义上代表整个目录）
     └── 目录路径 → 构建目录级图谱
           （自底向上，递归处理子目录 + 本目录文章）
```

### 行为

**构建文章**：
- 读取文章内容（纯文本提取）
- 增量判断（commitId + diff，小变化不重算）
- 需要时重新 AI 提取概念
- 写入/更新 `__graph__/{docId}.graph.json`
- 返回文章级概念列表

**构建目录**：
- 自底向上遍历（后序遍历）
- 每篇文章走「构建文章」逻辑
- 每个子目录递归走「构建目录」逻辑
- 汇总 + 本目录内归纳 + 合并子目录
- 写入 `___graph___.json`
- 返回目录级图谱（nodes + edges）

> **设计要点**：一个入口两种行为，调用方无需关心细节；目录构建内部复用文章构建逻辑。

## 构建流程

### 总体顺序：自底向上（后序遍历）

```
处理目录 X：
  1. 列出 X 目录下的子目录和文章
  2. 对每个子目录：
     ├── 已有 ___graph___.json → 检查是否过期（初版直接跳过子目录处理）
     └── 没有 → 递归处理该子目录
  3. 处理本目录每篇文章：
     ├── 已有 __graph__/{docId}.graph.json
     │   ├── lastIndexedCommitId == 当前 head → 直接复用
     │   └── commit 不同 → 重新提取，更新文章级隐藏文件
     └── 没有 → AI 提取 doc 节点，写入文章级隐藏文件
  4. 汇总本目录所有文章的 doc 节点（从各文章级文件读取）
  5. AI 从 doc 节点中归纳 concept 节点
  6. AI 生成 contains 关系（concept → doc，concept → concept）
  7. 合并子目录的 nodes + edges（去重）
  8. 写入本目录的 ___graph___.json
```

### 步骤详解

**Step 3：文章级 doc 节点提取与增量判断**
- 输入：单篇文章当前内容 + 文章级隐藏文件（如有）
- 判断逻辑：见上文「增量更新判断逻辑」
- 输出：更新或确认文章级 `__graph__/{docId}.graph.json
- 节点都是 `type: "doc"`，带 sources（来源文章信息）

**Step 5：归纳 concept 节点**
- 输入：本目录所有 doc 节点（label + description）
- 输出：concept 节点（type=concept，无 sources） + contains 边
- 要求：不强行归类，合并不了的节点独立存在；每个 concept 至少包含 2 个子节点
- 初版限定：一层归纳（doc → concept，共两层）

**Step 7：子目录合并**
- 节点去重：按 id 合并（doc 节点天然唯一；concept 节点按归一化 label/id）
- concept 合并：definition/description 取置信度最高的；confidence 取最高值
- 边去重：同 from + 同 to + 同 type 留一条，confidence 取最高值

### 初版范围限定

| 做 | 不做 |
|----|------|
| 文章级隐藏文件（doc 节点提取 + commitId 增量判断） | 跨目录归纳 concept（父目录只合并） |
| 目录级 `___graph___.json`（nodes + edges） | 多层深度归纳（初版最多一层） |
| doc + concept 两种节点类型 | 更多节点类型（如目录节点） |
| contains 一种关系 | related_to（后续加） |
| sources 精确到文章 + 可选标题 | 精确到段落/行号 |
| 自底向上构建 + 文章级增量 | 目录级增量缓存（初版每次全量合并） |
| AI 分析手动触发 | 保存时自动更新（后续可选） |
| 图谱可视化 + 节点详情 | 人工确认/编辑/删除 |

## 后端 API

| 接口 | 方法 | 说明 |
|------|------|------|
| `/api/domains/:domainId/graph` | GET | 获取全域图谱（递归聚合所有子目录） |
| `/api/domains/:domainId/graph/:dirPath` | GET | 获取指定目录的图谱（聚合该目录及其子树） |
| `/api/domains/:domainId/graph/analyze` | POST | 触发 AI 分析（指定目录或全域），异步返回任务 id |
| `/api/domains/:domainId/graph/analyze/:taskId` | GET | 查询分析任务状态 |

### 聚合逻辑

GET 图谱时的后端处理：
1. 读取目标目录的 `___graph___.json`
2. 递归读取所有子目录的 `___graph___.json`
3. 合并 nodes（按 id 去重，概念节点合并 sources）
4. 合并 edges（同 from+to+type 去重）
5. 返回 `{ nodes, edges }`

返回结构与隐藏文件的 nodes/edges 结构完全一致，前端直接可渲染。

## 接口定义

### 核心类型

```typescript
// 节点
type GraphNode = DocNode | ConceptNode;

interface DocNode {
  id: string;           // doc:{slug}
  type: 'doc';
  label: string;
  definition?: string;
  description: string;
  confidence: number;
  sources: DocSource[];
}

interface ConceptNode {
  id: string;           // concept:{slug}
  type: 'concept';
  label: string;
  definition?: string;
  description: string;
  confidence: number;
}

interface DocSource {
  type: 'doc';
  documentId: string;
  title: string;
  heading?: string;
}

// 边
interface GraphEdge {
  from: string;
  to: string;
  type: 'contains';
  confidence: number;
}

// 图谱
interface Graph {
  nodes: GraphNode[];
  edges: GraphEdge[];
}
```

### 核心入口（一个函数）

```typescript
interface GraphDeps {
  llm: { complete: (system: string, user: string) => Promise<string> };
  readMarkdown: (docPath: string) => Promise<string>;
  getCurrentCommitId: (docPath: string) => Promise<string>;
  readArticleCache: (docPath: string) => Promise<DocNode[] | null>;
  writeArticleCache: (docPath: string, nodes: DocNode[], commitId: string) => Promise<void>;
  listDir: (dirPath: string) => Promise<{ docs: string[]; dirs: string[] }>;
  readDirGraph: (dirPath: string) => Promise<Graph | null>;
  writeDirGraph: (dirPath: string, graph: Graph) => Promise<void>;
}

function buildGraph(target: string, deps: GraphDeps): Promise<Graph>
```

**行为：**
- target 是文章 → 提取 doc 节点，写文章级缓存，返回只有 doc 节点的 graph（edges 空）
- target 是目录 → 自底向上，递归处理子目录和文章，归纳 concept，生成 contains，写目录级文件，返回完整 graph

### 内部函数（纯逻辑，可单测）

```typescript
// LLM 链路（输入纯内容，输出不带 id/type/sources 的原始结构，由外层补全）
function extractDocNodes(markdown: string, llm: LLM): Promise<DocNodeStub[]>
function induceConceptNodes(docNodes: DocNode[], llm: LLM): Promise<ConceptNodeStub[]>
function generateContains(nodes: GraphNode[], llm: LLM): Promise<GraphEdge[]>

// 工具
function makeId(type: 'doc' | 'concept', label: string): string
function slugify(str: string): string
function mergeGraphs(a: Graph, b: Graph): Graph
function needRebuild(currentCommitId: string, cachedCommitId?: string): boolean
```

### 设计原则

- **FP 风格**：一个入口函数，所有 IO 通过 `GraphDeps` 注入
- **纯逻辑可测**：节点处理、合并、去重等不依赖 mdocs 运行时，可单独单测
- **AI 只处理内容**：LLM 链路只输入文本内容，输出纯知识结构，id / type / sources 由代码补全

## 风险与回滚

- **风险 1：AI 提取的概念质量差，图谱很乱** → 置信度过滤（默认只显示 ≥0.7 的）+ 可调节阈值
- **风险 2：概念命名不一致，导致去重失败** → 归一化规则 + 初版按名字匹配，后续可加语义去重
- **风险 3：全量分析 token 消耗大** → 文章级增量缓存（commitId + diff 判断），只重算变化大的文章
- **风险 4：聚合性能问题（大域文件多）** → 后端缓存聚合结果，文件变化时失效
- **风险 5：commit 历史读取耗时** → 初次全量构建后，后续增量只需对比变化文章的 commit diff
- **回滚**：删除所有 `__graph__/` 目录和 `___graph___.json` 文件即完全回退，不影响正文；前端入口可通过 feature flag 关闭

## 测试要点

- 文章级隐藏文件：doc 节点结构正确性、meta 字段（lastIndexedCommitId + needSync）正确性
- 增量判断：commit 相同跳过、commit 不同重算
- 单目录图谱：节点合并去重、contains 关系生成的正确性（抽样验证）
- 归纳逻辑：concept 节点生成、contains 关系建立的合理性（抽样验证）
- 聚合逻辑：多级目录下节点去重、边去重的正确性
- 权限过滤：私有文档的节点、概念和关系对无权用户不可见
- 文档树过滤：`___graph___.json` 和 `__graph__/` 不出现在文档列表和树中
- concept 去重：同名 concept 合并后 definition/description 的处理
- API 返回格式：与目录级文件 nodes/edges 结构一致，前端可直接渲染
- 目录重命名/移动：对应图谱隐藏文件和目录同步移动
- 独立模块可单测：合并、去重、增量判断等纯逻辑不依赖 mdocs 运行时
