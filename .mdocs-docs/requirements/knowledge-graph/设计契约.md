## 方案摘要

每个目录下新增 `___graph___.json` 隐藏文件，由 AI 自动分析生成：从文章中提取知识节点（doc 节点，带来源），再从知识节点中归纳出概念（concept 节点，不带来源），建立 contains 层级关系。构建按目录自底向上，父目录聚合所有子目录的完整图谱（节点 + 边全量透传）。**每层只拿入度为 0 的顶层节点喂给 AI 归纳**，避免下层已归类节点被重复处理。AI 通过 tool 调用输出结构化数据（正常 tool + 降级 tool，外部不感知降级实现）。前端提供图谱页面，以力导向图可视化呈现，用户可点击节点查看定义/描述和来源。**AI 全自动，人零干预**。

整体架构：

```
┌──────────────────────────────────────────────┐
│  图谱页面（前端）                             │  ← 力导向图可视化 + 节点详情
├──────────────────────────────────────────────┤
│  Graph API（后端）                           │  ← 读 JSON、触发分析
├──────────────────────────────────────────────┤
│  AI 分析（pi-agent + tool 方式输出）          │  ← 提取节点、归纳概念、生成关系
├──────────────────────────────────────────────┤
│  ___graph___.json（每目录一份，完整子树图谱）  │  ← 结构化存储：所有 nodes + 所有 edges
└──────────────────────────────────────────────┘
```

## 隐藏文件设计

### 两层结构

知识图谱的隐藏文件分两层：

| 层级 | 文件 | 内容 | 说明 |
|------|------|------|------|
| 文章级 | `__graph__/{documentId}.graph.json` | 单篇文章提取的知识节点（doc 类型） + meta | 知识提取的缓存，用于增量更新 |
| 目录级 | `___graph___.json` | 节点（doc + concept） + 边（完整图谱） | 目录内所有知识的关系网络 |

文章级只有节点（doc 类型，没有边），目录级才有完整的 nodes + edges。doc 节点是目录级的"原材料"，concept 节点是从 doc 节点中进一步归纳出来的。

所有隐藏文件通过 mdocs 文件存储系统读写（与普通文档共用同一套 file-store），不出现在文档树和搜索结果中。

### 文章级隐藏文件

**路径**：`{目录}/__graph__/{documentId}.graph.json`

落盘是**完整图文件对象**（与目录级同一家族），不是裸 `nodes` 数组。

```json
{
  "version": 1,
  "meta": {
    "commitId": "commit-abc123",
    "dirty": false
  },
  "nodes": [
    {
      "id": "doc:recovery-code-intro",
      "type": "doc",
      "label": "恢复码是什么",
      "definition": "恢复码是一串由系统生成的字符序列，用于在丢失访问凭证时恢复访客身份。",
      "description": "基于 SHA-256 哈希生成，一次性使用。",
      "confidence": 0.9,
      "sources": [
        {
          "type": "doc",
          "documentId": "doc-uuid-123",
          "title": "恢复码",
          "heading": "什么是恢复码"
        }
      ]
    }
  ],
  "edges": []
}
```

#### 文章 meta 字段

| 字段 | 类型 | 说明 |
|------|------|------|
| `meta.commitId` | string | **上次成功抽取图谱时**的文章 head commitId。未超阈值的小改**不得**改写此字段 |
| `meta.dirty` | boolean | `true` = 下次构建必须重提；`false` = 可直接复用本文件 nodes |

> 兼容：旧文件若为 `{ commitId, nodes }`，读取时升格为 `meta.commitId` + `meta.dirty=false` + `edges=[]`。

#### 文章级：构建时是否重提

**只看 `meta.dirty`**（有缓存且 `dirty === false` → 跳过 AI 提取；否则重提并写回 `dirty=false`、更新 `commitId`）。

新增文章：不预创建隐藏文件；等某次目录/域构建走到该文再惰性提取。

#### 发布后异步：是否置 dirty（变化率）

发布成功后**异步**（不阻塞发布）执行：

1. 若无该文文章级隐藏文件 → **结束**（不打标、不蔓延）
2. 读缓存 `meta.commitId`，取出**当时** commit 的 Lexical blob
3. 取**当前**文章 Lexical
4. 两侧均经 mdocs 内容提取器（`extractPlainTextFromLexical`）得到正文
5. 算行级变化率（非 merge UI 的 inline diff）：
   `ratio = (addedLines + removedLines) / max(oldLineCount, 1)`
6. `ratio >= 阈值` → `meta.dirty = true`，并 `markAncestorsDirty(该文)`；未达阈值 → 不改 dirty、**不改** `commitId`

阈值初版可配置常量（实现时定默认，如 `0.15`），契约不锁死具体数字。

> 原则：目录事件 / 发布事件**只维护缓存脏标**，不沿知识边修订图谱；知识结构只在显式构建时重投影。

### 目录级隐藏文件

**路径**：`{目录}/___graph___.json`（域级同结构，落在域根）

```json
{
  "version": 1,
  "meta": {
    "dirty": false
  },
  "nodes": [],
  "edges": []
}
```

#### 目录 / 域 meta 字段

| 字段 | 类型 | 说明 |
|------|------|------|
| `meta.dirty` | boolean | `true` = 下次构建本层必须重跑汇总+归纳；`false` = 可整包复用本文件 |

> **本期不做 `sourceHash` / 内容 hash 短路**：标了 dirty 就重算；未 dirty 直接返回缓存。若日后要在「已 dirty 但仍想省 LLM」上加第二道闸，再引入 `sourceHash`。

#### 目录级：构建时是否重算

**只看 `meta.dirty`**：

- `dirty === false` 且文件存在 → **不 walk 子树、不跑 AI**，直接返回缓存（可选优化：仍可 walk，但本期允许整包跳过）
- `dirty === true` 或无文件 → 后序构建子节点 → `aggregateAndInduce` → 写回并 `dirty=false`

子节点中未 dirty 的文章/目录仍走各自缓存短路。

### 脏标蔓延（`markAncestorsDirty`）

目录**不会自己变脏**；只由文章侧（或结构变动）沿 **`parent_id` 向上**点燃。

```text
markAncestorsDirty(startDocumentId):
  // start 可以是文章，也可以是「旧/新父目录」本身
  p = load(startDocumentId).parent_id   // 若 start 已是目录，实现可约定从 start 自身开始标
  while p != null:
    folder = load(p)                    // 应为 dir
    若存在该目录 ___graph___.json:
      meta.dirty = true
    // 无隐藏文件 → 本层 noop，继续向上
    p = folder.parent_id
  若存在域级 ___graph___.json:
    meta.dirty = true
```

| 事件 | 动作 |
|------|------|
| 发布变化率超阈值 | 文章 `dirty=true` + `markAncestorsDirty(文章)` |
| 删除文章 | **先**根据仍在库中的文章记下 `parent_id` / `domain_id`，执行 `markAncestorsDirty`（已有目录/域图置 `dirty`）；**再**删文章级缓存（DB+盘）；最后才删正文。不可先删正文再上爬——否则丢 parent 链 |
| 移动文章 | **先**对旧父链、新父链 `markAncestorsDirty`；**再**删旧文章级缓存；不搬缓存、新目录不预创建 |
| 新增文章 | 本期可不预标；构建时自然纳入。若 UI 要「图过期」提示，可对父链 `markAncestorsDirty` |
| 删除目录 | **先**对更上层祖先 `markAncestorsDirty`；**再**子树内全部删除（含 graph 隐藏文件 DB+盘） |

复杂度：沿 `parent_id` 上爬 **O(深度)**，禁止「先捞全域文章再 BFS」。

### 文档树中的过滤

以下文件/目录不出现在文档树和搜索结果中：
- `___graph___.json`（目录级图谱文件）
- `__graph__/`（文章级图谱缓存目录）
- 与 `desc.md` 同级，属于特殊保留名

### 隐藏文件生命周期（删 / 挪 / 删目录）

图谱是**某次构建对当时文档快照的投影**；隐藏文件是构建产物缓存。目录结构 ≠ 知识结构——CRUD **只失效缓存（dirty / 删除）**，不尝试精确改知识节点。

| 用户操作 | 隐藏文件怎么处理 |
|----------|------------------|
| **删除文章** | **先** `markAncestorsDirty`（文章尚在，沿 `parent_id` 上爬，已有目录/域图 `dirty=true`），**再**删 `{documentId}.graph-file`（DB+盘），最后删正文 |
| **移动文章** | **先**旧父+新父祖先链 dirty，**再**删旧文章级缓存；不搬缓存；新目录不预创建 |
| **删除目录** | **先**上层祖先 dirty，**再**子树内普通文档与 graph 隐藏文件 **DB+磁盘都清** |

补充：

- **惰性创建**：隐藏文件只在图谱构建写路径创建
- **不做**：移动时 rename `__graph__/{id}.graph.json` 到目标目录
- GET：若缓存 `dirty===true`，可仍返回旧 nodes/edges，但应让前端可知过期（实现：响应带 `meta.dirty` 或等价）；权威刷新靠再次「生成图谱」

## 节点与边（数据字段）

### 节点字段说明

所有节点都是**知识节点**，按来源分为两种 type。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | string | 格式 `{type}:{slug}`，全局唯一 |
| `type` | string | `"doc"` 或 `"concept"` |
| `label` | string | 节点名称/标题（显示用） |
| `definition` | string | 准确定义。有则填，可为空 |
| `description` | string | 一段描述。**至少有这个，不能为空** |
| `confidence` | number | AI 置信度 0-1 |
| `sources` | array | **只有 doc 类型有**：来源文章列表。代码填充，AI 不输出 |

> **doc vs concept 的区别**：doc 节点是从**单篇文章**中直接提取的知识块，所以有 sources；concept 节点是从**多个已有节点（doc 或 concept）** 中归纳抽象出来的概念，没有 sources。

### Sources 字段说明

每个 source 对象（目前只有 doc 一种类型）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `type` | string | 固定 `"doc"` |
| `documentId` | string | 来源文档 id |
| `title` | string | 来源文章标题（冗余，便于展示） |
| `heading` | string | 可选，来源文章内的标题锚点 |

### 边字段说明

| 字段 | 类型 | 说明 |
|------|------|------|
| `from` | string | 起点节点 id |
| `to` | string | 终点节点 id |
| `type` | string | 关系类型 |
| `confidence` | number | AI 置信度 0-1 |

### 关系类型定义

| 类型 | 方向 | 说明 | 初版 |
|------|------|------|------|
| `contains` | concept → doc / concept → concept | A 包含 B（A 更抽象/宽泛，B 更具体） | P0 |
| `related_to` | 任意节点 ↔ 任意节点 | 两个节点有语义关联 | P1 |

> contains 的方向：上层 → 下层（抽象 → 具体）。所以 concept 可以包含 doc，也可以包含更具体的 concept。

### 节点命名与去重规则

- 节点 id 由 `{type}:` + label 归一化 slug 组成
- 归一化规则：转小写、去首尾空格、中文/英文数字保留、特殊字符替换为 `-`
- doc 节点 id 中可以包含文章标识（如 `doc:recovery-code-intro`），由 AI 或代码生成时保证唯一性
- concept 节点按 label 去重：同一目录内同名 concept 自动合并，取最高置信度的 definition/description 和 confidence
- 跨目录合并时同理（聚合时处理）

## 技术决策记录

### 决策 1：增量 diff 与 AI 输入都用 Markdown，引入 lobe headless

- **状态**：partially superseded（2026-08-26）
- **上下文**：
  - 文章级隐藏文件需要增量判断（变化大才重算概念，小修改跳过）
  - commit blob 和当前文档内容都是 Lexical JSON 格式
  - 直接 diff JSON 字符串无意义（节点 id、format 等元数据噪音大）
- **现行决策（2026-08-26）**：
  - 发布后异步用 `extractPlainTextFromLexical` 提取正文，再算**行级变化率**决定 `dirty`
  - 构建跳过只看 `meta.dirty`，不再「commit 一变就重提」
  - AI 抽取输入仍可用纯文本；升 Markdown / lobe headless **不阻塞本补丁**
- **原决策（保留作后续优化）**：两端转 Markdown 再 diff；引入 lobe headless
- **后果**：本补丁不强制上 lobe；阈值与提取器可单测

### 决策 2：AI 分析拆为三条独立链路（三次独立调用）

- **状态**：accepted（初版）
- **上下文**：
  - 图谱构建需要 AI 参与的环节有三个：概念提取、上层归纳、关系生成
  - 可以一次调用让 AI 输出全部结果，也可以拆成三次调用
- **决策**：拆为三条独立链路，每次调用只做一件事
  1. **extractConcepts**：文章 → 概念列表
  2. **induceUpperNodes**：下层概念 → 上层概念节点
  3. **generateContainsRelations**：全部概念 → contains 关系列表
- **理由**：
  - 每次任务更聚焦，AI 输出质量更可控
  - 输出结构更简单，出错概率低
  - 方便单独调试和优化 prompt
  - 某条链路失败不影响其他链路（可以重试或降级）
  - 以后扩展其他关系类型（related_to 等），就是新增一条链路
- **后果**：
  - 多两次 API 调用，token 成本略高
  - 每次调用要等结果，总耗时略长
  - 但图谱构建是后台异步的，耗时和成本可以接受

### 决策 3：输出用自然语言 label 关联，不用 id；用 JSON + Zod 校验，失败重试一次

- **状态**：accepted（初版）
- **上下文**：
  - AI 输出关联关系时，可以用 id 关联，也可以用 label（概念名）关联
  - 输出格式可以是纯文本、JSON、XML 等
- **决策**：
  - AI 输出用 **label（中文名）** 关联，不用 id
  - 输出格式强制 **JSON**，用 Zod 做结构化校验
  - 解析/校验失败时，**把错误信息返回给 AI 重试一次**，再失败才抛错
  - JSON 容错：支持 code fence、自动提取最外层 JSON 对象
- **理由**：
  - AI 对自然语言（label）的把握远比对格式规则（slug/id）强，出错率低
  - Zod 校验保证输出结构正确，类型安全
  - 一次重试能解决大部分格式问题，成本不高
- **后果**：
  - 代码里需要做 label → id 的映射转换
  - 存在同名概念冲突风险（初版规模下概率低，冲突时报错或加后缀处理）

## LLM 交互设计

### 总体架构

```
业务层（GraphLLM 接口）
    ↓ 每条链路一个文件
Prompt + 解析封装层
    ↓ 共用
JSON 容错提取 + Zod 校验 + 单轮重试
    ↓
底层 LLMProvider（pi-ai / Anthropic 兼容）
```

底层 Provider 只有一个 `complete(system, user): Promise<string>` 方法，不感知业务。业务层通过 prompt 定义任务，解析封装层负责格式正确性。

### 链路 1：extractDocNodes（从文章提取 doc 节点）

- **触发**：构建单篇文章时
- **输入**：文章 Markdown 全文 + 文档元信息（标题、id）
- **输出**：doc 节点列表（label、definition?、description、confidence、sourceHeading?）
- **Prompt 要点**：
  - 角色：知识提取专家
  - 从文章中提取 3-10 个知识要点，每个要点是一个独立的知识节点
  - 每个节点至少有 description，优先有 definition
  - 标记来源标题（能对应上的话）
  - 只输出 JSON，不要多余文字
- **代码补充**：生成 id（`doc:{slug}`） / type=doc / sources（type=doc，填入 documentId、title、heading）

### 链路 2：induceConceptNodes（从 doc 节点归纳 concept 节点）

- **触发**：构建目录时，汇总完本目录所有 doc 节点后
- **输入**：当前目录范围内所有 doc 节点（label + description）
- **输出**：concept 节点列表（label、description、confidence）
- **Prompt 要点**：
  - 角色：知识归纳专家
  - 从知识节点中归纳出若干上层概念（数量约为总数的 1/3 ~ 1/5）
  - 每个概念是对多个相关知识节点的抽象概括
  - 允许多父（一个 doc 节点可属于多个 concept）
  - 合并不了的可以不归（不强求全覆盖）
  - 只输出 JSON
- **代码补充**：生成 id（`concept:{slug}`） / type=concept；concept 节点没有 sources

### 链路 3：generateContainsRelations（生成 contains 关系）

- **触发**：生成 concept 节点后
- **输入**：全部节点（doc + concept）的 label + description + type
- **输出**：contains 关系列表（fromLabel、toLabel、confidence）
- **Prompt 要点**：
  - 角色：知识图谱关系专家
  - 判断包含关系（A contains B = A 更抽象/宽泛，B 更具体）
  - from = 上层（更抽象），to = 下层（更具体）
  - concept 可以包含 doc，也可以包含更具体的 concept
  - 只输出高置信度的关系，宁缺毋滥
  - 只输出 JSON
- **代码补充**：
  - label → id 转换
  - 生成 GraphEdge（type='contains'）

### 容错与校验

所有链路共用同一套容错策略：

1. **JSON 提取**：去除 ``` 围栏，提取最外层 `{...}`
2. **JSON.parse**：解析失败进入重试
3. **Zod 校验**：字段类型、必填项、数值范围校验，失败进入重试
4. **重试机制**：把错误信息附加到 user prompt 中，让 AI 修正输出，最多重试 1 次
5. **最终失败**：向上抛出异常，由上层决定如何处理

## 统一入口

### 入口设计

图谱构建只有**一个入口**，给定一个路径（文档或目录），为其构建知识图谱：

```typescript
buildKnowledgeGraph(target: string): Promise<GraphResult>
```

### 判断逻辑

```
给定 target：
  1. 判断 target 指向什么：
     ├── 普通 .md 文章 → 构建文章级图谱
     │     （更新 __graph__/{docId}.graph.json，含增量判断）
     ├── ___desc___.md → 当作目录处理
     │     （目录描述文件语义上代表整个目录）
     └── 目录路径 → 构建目录级图谱
           （自底向上，递归处理子目录 + 本目录文章）
```

### 行为

**构建文章**：
- 读取文章内容（纯文本提取）
- 增量判断（commitId + diff，小变化不重算）
- 需要时重新 AI 提取概念
- 写入/更新 `__graph__/{docId}.graph.json`
- 返回文章级概念列表

**构建目录**：
- 自底向上遍历（后序遍历）
- 每篇文章走「构建文章」逻辑
- 每个子目录递归走「构建目录」逻辑
- 汇总 + 本目录内归纳 + 合并子目录
- 写入 `___graph___.json`
- 返回目录级图谱（nodes + edges）

> **设计要点**：一个入口两种行为，调用方无需关心细节；目录构建内部复用文章构建逻辑。

## 构建流程

### 总体顺序：自底向上（后序遍历 TreeNode）

```
处理节点 X：
  ├── X 是 document 节点 → 走文章级提取流程
  └── X 是 folder 节点 →
       1. 对每个子节点递归调用 buildGraph（后序遍历）
       2. 汇总所有子节点的完整图谱（nodes + edges 全量透传）
       3. 计算「入度为 0」的顶层节点（未被任何 contains 边指向的）
       4. AI 基于顶层节点归纳 concept 节点
       5. AI 生成 contains 关系（本层 concept → 下层顶层节点）
       6. 组装本层完整图谱：所有下层节点 + 本层 concept + 所有下层 edges + 本层 edges
       7. 写入本目录的图谱缓存（___graph___.json）
```

> **关键设计**：每层都存完整子树图谱（所有节点 + 所有边），渲染时读一个文件即可。
> 但喂给 AI 归纳 / 生成关系时，只输入「入度为 0」的顶层节点，
> 避免下层已经被归类的节点被重复处理，保证层级清晰。

### 步骤详解

**Step 3：文章级 doc 节点提取与增量判断**
- 输入：单篇文章当前内容 + 文章级隐藏文件（如有）
- 判断逻辑：见上文「增量更新判断逻辑」
- 输出：更新或确认文章级 `__graph__/{docId}.graph.json
- 节点都是 `type: "doc"`，带 sources（来源文章信息）

**Step 5：归纳 concept 节点**
- 输入：本目录所有「入度为 0」的顶层节点（label + description）
- 输出：concept 节点（type=concept，无 sources）
- 要求：不强行归类，合并不了的节点独立存在；每个 concept 至少包含 2 个子节点
- 节点 id 带 4 位随机后缀，天然唯一，无需去重
- AI 通过 tool 调用输出结构化结果，无内容时调用降级 tool 返回空数组（外部不感知）

**Step 6：生成 contains 关系**
- 输入：本层归纳出的 concept 节点 + 所有顶层节点
- 输出：本层新增的 contains 边（concept → 下层节点）
- 下层已有的 edges 全部透传，不做修改

**Step 7：组装完整图谱**
- 节点 = 所有下层节点 + 本层新增 concept（按 id 天然唯一，无需去重）
- 边 = 所有下层 edges + 本层新增 edges（同 from+to+type 自然不重复）
- 完整图谱写入本层 `___graph___.json`，供上层读取和渲染使用

### 初版范围限定

| 做 | 不做 |
|----|------|
| 文章级隐藏文件（doc 节点提取 + commitId 增量判断） | 人工确认/编辑/删除节点 |
| 目录级 `___graph___.json`（完整子树图谱：所有 nodes + edges） | 多层深度概念归纳（逐层向上一层一层来，不是直接多层） |
| doc + concept 两种节点类型 | 更多节点类型（如目录节点） |
| contains 一种关系 | related_to（后续加） |
| sources 精确到文章 + 可选标题 | 精确到段落/行号 |
| 自底向上构建 + 文章/目录 `meta.dirty` 短路 | `sourceHash` 第二道闸（本期不做） |
| AI 分析手动触发 | 保存时自动更新（后续可选） |
| 图谱可视化 + 节点详情 | 节点 id 去重合并（id 带随机后缀天然唯一） |
| AI 输出用 tool 方式（正常 + 降级 tool，外部不感知） | 纯文本 JSON 输出 |

| 接口 | 方法 | 说明 |
|------|------|------|
| `/api/domains/:domainId/graph` | GET | 获取全域图谱（递归聚合所有子目录） |
| `/api/domains/:domainId/graph/:dirPath` | GET | 获取指定目录的图谱（聚合该目录及其子树） |

| `/api/domains/:domainId/graph/analyze/:taskId` | GET | 查询分析任务状态 |

### 读取逻辑

GET 图谱时的后端处理：
1. 读取目标目录的 `___graph___.json`
2. 直接返回 `{ nodes, edges }`（每层存完整子树图谱，无需递归聚合）

返回结构与隐藏文件的 nodes/edges 结构完全一致，前端直接可渲染。

## 接口定义

### 核心类型

```typescript
// 节点
type GraphNode = DocNode | ConceptNode;

interface DocNode {
  id: string;           // doc:{slug}
  type: 'doc';
  label: string;
  definition?: string;
  description: string;
  confidence: number;
  sources: DocSource[];
}

interface ConceptNode {
  id: string;           // concept:{slug}
  type: 'concept';
  label: string;
  definition?: string;
  description: string;
  confidence: number;
}

interface DocSource {
  type: 'doc';
  documentId: string;
  title: string;
  heading?: string;
}

// 边
interface GraphEdge {
  from: string;
  to: string;
  type: 'contains';
  confidence: number;
}

// 图谱
interface Graph {
  nodes: GraphNode[];
  edges: GraphEdge[];
}
```

### 核心入口（一个函数）

```typescript
import type { TreeNode } from '@shared/types/tree';

interface GraphDeps {
  llm: { complete: (system: string, user: string) => Promise<string> };
  // 单篇文档操作
  readMarkdown: (documentId: string) => Promise<string>;
  getCurrentCommitId: (documentId: string) => Promise<string>;
  readArticleCache: (documentId: string) => Promise<{ nodes: DocNode[]; commitId: string } | null>;
  writeArticleCache: (documentId: string, nodes: DocNode[], commitId: string) => Promise<void>;
  getDocTitle: (documentId: string) => Promise<string>;
  // 目录级图谱缓存（folderId = 目录的 documentId）
  readDirGraph: (folderId: string) => Promise<Graph | null>;
  writeDirGraph: (folderId: string, graph: Graph) => Promise<void>;
}

function buildGraph(rootNode: TreeNode, deps: GraphDeps): Promise<Graph>
```

**输入：**
- `rootNode: TreeNode` — 根节点（folder 或 document 都可以），从 mdocs tree 接口获取
- 后序遍历这棵树，自底向上构建图谱

**行为：**
- 文档节点 → AI 提取 doc 节点，写文章级缓存，返回只有 doc 节点的 graph（edges 空）
- 目录节点 → 汇总所有子节点图谱 → 归纳 concept → 生成 contains → 写目录级缓存 → 返回完整 graph

**设计要点：**
- 不直接操作文件系统，所有存储通过 mdocs 抽象层
- 目录遍历基于 TreeNode，不依赖路径或文件系统结构
- 所有 IO 通过 GraphDeps 注入，核心模块纯逻辑可单测

### 内部函数（纯逻辑，可单测）

```typescript
// LLM 链路（输入纯内容，输出不带 id/type/sources 的原始结构，由外层补全）
function extractDocNodes(markdown: string, llm: LLM): Promise<DocNodeStub[]>
function induceConceptNodes(docNodes: DocNode[], llm: LLM): Promise<ConceptNodeStub[]>
function generateContains(nodes: GraphNode[], llm: LLM): Promise<GraphEdge[]>

// 工具
function makeId(type: 'doc' | 'concept', label: string): string
function slugify(str: string): string
function mergeGraphs(a: Graph, b: Graph): Graph
function needRebuild(currentCommitId: string, cachedCommitId?: string): boolean
```

### 设计原则

- **FP 风格**：一个入口函数，所有 IO 通过 `GraphDeps` 注入
- **纯逻辑可测**：节点处理、合并、去重等不依赖 mdocs 运行时，可单独单测
- **AI 只处理内容**：LLM 链路只输入文本内容，输出纯知识结构，id / type / sources 由代码补全

## 风险与回滚

- **风险 1：AI 提取的概念质量差，图谱很乱** → 置信度过滤（默认只显示 ≥0.7 的）+ 可调节阈值
- **风险 2：概念命名不一致，导致去重失败** → 归一化规则 + 初版按名字匹配，后续可加语义去重
- **风险 3：全量分析 token 消耗大** → 文章级增量缓存（commitId + diff 判断），只重算变化大的文章
- **风险 4：聚合性能问题（大域文件多）** → 后端缓存聚合结果，文件变化时失效
- **风险 5：commit 历史读取耗时** → 初次全量构建后，后续增量只需对比变化文章的 commit diff
- **回滚**：删除所有 `__graph__/` 目录和 `___graph___.json` 文件即完全回退，不影响正文；前端入口可通过 feature flag 关闭

## 测试要点

- 文章级隐藏文件：完整 `GraphFile`（`meta.commitId` + `meta.dirty` + nodes + edges）
- 构建短路：文章/目录 `dirty===false` 跳过 AI；`dirty===true` 必重算并清 dirty
- 发布异步：无缓存不打标；小变化不 dirty、不改 commitId；大变化文章 dirty + 祖先目录 dirty
- `markAncestorsDirty`：沿 `parent_id` 上爬；无目录图则跳过该层继续向上；域图一并处理
- 删文章：**先**祖先 dirty，**再**清文章级缓存与正文；祖先目录图保留文件仅标 dirty
- 移文章：**先**旧父+新父 dirty，**再**删旧文章级缓存；新目录无预创建
- 删目录：**先**上层 dirty，**再**子树 graph DB+盘都删
- 变化率纯函数单测；脏标蔓延可不依赖 LLM 的集成测
- 文档树过滤：图谱隐藏文件不出现在树中
- API：可返回 nodes/edges；dirty 提示可选
