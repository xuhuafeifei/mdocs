# agent-session-meta-integrity — 需求分析

> 一句话：修好智能助手「历史会话列表莫名只剩一条」——锁住 `session.json` 读改写，并提供运维 CLI 从孤儿 `*.jsonl` 重建索引。

## 背景

- 智能助手历史列表只读 `tenant/{visitorId}/agent/session/session.json` 的 `sessions[]`。
- 对话正文在同目录 `{sessionId}.jsonl`。**没有自动按天清理 session**（契约备忘未做）。
- 实机现象：同一访客目录下有大量 `*.jsonl`，但 `session.json` 的 `sessions` 只剩 1 条 → UI 像「聊着聊着历史没了」。
- 根因（待契约确认后固化）：`session.json` 无锁整文件覆盖写；并发 `touchLastOpened` / `ensureLastOpened` 等读改写会丢条目；若读到半截 JSON 导致 `readMeta()===null`，随后用「空 `sessions` + 当前一条」写回，索引被重置。

## 目标

1. **`session.json` 读改写加锁**（进程内串行 + 跨进程文件锁），并 **原子写**（tmp + rename），避免半截 JSON。
2. **读失败时禁止写成「只剩当前一条」**：优先从目录内 `*.jsonl` 恢复索引再改写。
3. **运维 CLI**：在服务端用命令扫描并修复索引（不删 jsonl）；支持 dry-run / confirm。
4. **不新增设置页 UI**（产品明确不要管理界面）。

## 非目标（本期不做）

- 会话删除 / 重命名 / 管理 UI  
- 按天数自动 GC session  
- 把对话迁入 SQLite  
- 改 jsonl 行格式或把 tool/thinking 入档  
- 跨访客共享 session  

## 验收标准

1. 并发多轮 append（或模拟并发 `touchLastOpened`）后，`sessions[]` 条数不丢（与磁盘 jsonl 集合一致或为其超集中的正确子集策略见设计契约）。  
2. 人为制造「meta 只有 1 条、目录有 N 个 jsonl」时，执行 repair `--confirm` 后列表恢复为 N（或 N 与原有 meta 并集）。  
3. `--dry-run` 不改磁盘；`--confirm` 才写 `session.json`。  
4. 正常 chat / 「+」新建 / 历史切换行为与现网一致，无回归。
