# agent-session-meta-integrity — 设计契约

> **状态**：已同意（2026-10-10，随 v1.3.23 发布）

## 方案摘要

### 问题模型

| 层 | 职责 | 丢失表现 |
|----|------|----------|
| `{sessionId}.jsonl` | 对话正文（一行一条 user/assistant） | 一般仍在（非清理） |
| `session.json` | **索引**：`lastOpenedSessionId` + `sessions[]`（id/title/updatedAt…） | 并发覆盖 / 读失败重置 → UI 历史列表「没了」 |

历史下拉**只读** `sessions[]`，不扫目录 jsonl——所以索引被写短，界面就空，磁盘对话还在。

### `readMeta` 是什么

`AgentSessionManager` 的私有方法：读磁盘上的 `session.json`，解析成内存对象；失败返回 `null`（**不抛错**）。

路径：`{dataDir}/tenant/{visitorId}/agent/session/session.json`（coding 则为 `…/coding-session/session.json`）。

返回 `null` 的条件（任一即 `null`）：

| 情况 | 说明 |
|------|------|
| 文件不存在（ENOENT） | 首次使用 |
| `JSON.parse` 失败 | 写到一半被读到、内容损坏 |
| `lastOpenedSessionId` 缺失或不是合法 UUID | 校验过严，整份 meta 作废 |
| 其它读 IO 错误 | catch 后同样 `null` |

注意：`sessions` 缺省时会被当成 `[]`，但只要 `lastOpenedSessionId` 合法，**仍算读成功**（空列表）。真正危险的是整份变 `null` 后，旧写路径用空列表当起点再落盘。

### 哪些操作会改 `session.json`

全部是「读 meta → 改内存 → **整文件覆盖写**」。旧实现无锁、非原子写。

| 用户/系统动作 | HTTP / 调用链 | manager 方法 | 对 meta 做什么 |
|---------------|---------------|--------------|----------------|
| 发一条助手消息（一轮 chat） | `POST /api/agent/chat` → run → pi | **`appendUser`** 然后（回复结束）**`appendAssistant`** | 各调一次 **`touchLastOpened`**：更新 `lastOpened`、该 session 的 `updatedAt`；首条 user 还可写 `title`。**一轮 chat 至少写 meta 两次** |
| 打开面板 / 拉当前会话 | `GET /api/agent/session` | `loadLastOpenedMessages` → **`ensureLastOpened`** | 保证有 lastOpened；可能补齐 entry 并写回 |
| 打开历史列表 | `GET /api/agent/sessions` | `listSessions` → **`ensureLastOpened`** 再读 | 同上，ensure 可能写 |
| 点「+」新建 | `POST /api/agent/sessions` | **`createSession`** | 新 UUID 插入 `sessions`，设为 lastOpened |
| 点历史某条切换 | `POST /api/agent/session/open` | **`openSession`** | 改 lastOpened，touch 该条 |
| 帮写绑定文档 | `POST /api/agent/session/bind-document` | **`bindSessionDocument`** | coding：改 entry 的 `documentId` / lastOpenedByDocument |
| 用量等旁路 | `context-usage` 等 | `loadLastOpenedMessages` → ensure | 可能写 |

**最常见压力**：同访客快速连聊或双标签时，多路 `touchLastOpened` / `ensureLastOpened` 交错。

**不改 `session.json` 的**：只 `appendFile` 写 `{id}.jsonl` 的那半步——但 append 之后几乎总会 `touchLastOpened` 再改 meta。

### 为何会变成「只剩一条」（两条独立机制）

**先澄清：交错覆写 ≠ 写成空 `[]`。**

机制 A 里，后写的一方手里通常仍是「自己读到时那份非空列表」（比如 10 条），盖回去还是 10 条，只是**丢掉读之后别人新增的那些**。  
磁盘上的 `sessions` **不会因为单纯丢更新就变成 `[]`**。  
旧代码里出现的 `sessions: []`，是 `readMeta()===null` 时**内存里临时拼的默认对象**，紧接着会把「当前 sessionId」ensure 进去再写盘 → 落盘结果是 **1 条**，不是空数组。此前契约若写成「清空成 []」不准确，以本节为准。

**机制 A — 丢更新（lost update，JSON 仍合法，列表变短但不必然变 1）**

```
时刻1  请求A readMeta → sessions = [S1…S10]
时刻2  请求B readMeta → sessions = [S1…S10]   （A 尚未写完）
时刻3  请求A 新建 S11，write 成 [S1…S11]
时刻4  请求B 只改 S10 的 updatedAt，按自己手里的 [S1…S10] write
结果   磁盘 meta 回到 10 条，S11 从索引消失；S11.jsonl 可能已存在 → 孤儿
```

反复交错会越挤越少，但每一步仍是「用某次读到的快照整文件盖回去」。

**机制 B — 读失败后「从空列表当起点」再只 ensure 当前（一次变 1 条）**

旧代码模式（概念上）：

```text
meta = readMeta()
if meta == null:
  meta = { lastOpenedSessionId: 当前sessionId, sessions: [] }  // 仅内存起点，不是最终空文件
ensureSessionEntry(meta, 当前sessionId)  // sessions 变为长度 1
writeMeta(meta)  // 整文件覆盖 → 索引只剩当前这一条；其余 id 的 jsonl 仍在
```

`readMeta()===null` 常见触发：另一次非原子 `writeFile` 写到一半被读到 → `JSON.parse` 失败；或 `lastOpenedSessionId` 非法导致整份作废。  
**这才是「大量 jsonl + sessions.length===1」的主因模型**；机制 A 负责制造孤儿与变少，机制 B 负责一次性打成一条。

### 方案

**核心：在 `AgentSessionManager` 公开方法级排队（对齐 agent-demo `createSerialExecutor`）**

落盘只应走 Manager（`loadLastOpenedMessages` / `createSession` / `openSession` / `appendUser` / `appendAssistant` / `listSessions`→ensure / `repair…`）。  
Chat 只调用这些接口，**不**直接碰 `session.json` / jsonl。  
因此串行点应放在 **Manager 方法入口**，而不是 Chat，也不是「只锁 writeFile」。

agent-demo（`watch-dog/serial-sql.ts`）模式：同一 key 上 `execute(task)` Promise 链——前一个方法整段结束后，后一个才开始。

```text
队列 key = 该 Manager 的 session 目录（或等价 metaPath）
A.appendUser 整段结束 → B.appendAssistant / createSession / … 才开始
```

这样从根上消掉「读旧 meta 再覆写」。实现上可把队列挂在 Manager 实例或按 `sessionDir` 全局复用（多实例同目录须共享同一 executor）。

| 项 | 约定 |
|----|------|
| 进程内排队 | **所有会读改磁盘会话状态的 Manager 公开方法入队**（含 append 的 jsonl+meta、create/open/ensure/repair） |
| 跨进程（可选增强） | 队内再抢 `{meta}.lock`；单进程部署时队列已够 |
| 原子写 | `session.json` 仍 tmp+rename，防半截 JSON |
| 读失败恢复 | 同前 |
| CLI repair | 走同一 Manager/队列 |
| UI | **不做** |

**非目标：** Chat / run 层再套一层 visitor 聊天互斥（防双标签并行跑模型）——另开需求。

### CLI 行为

```
mdocs agent session repair --dry-run
mdocs agent session repair --confirm
mdocs agent session repair --visitor <id|name> --kind normal --confirm
```

- 未传 `--visitor`：扫描 `{dataDir}/tenant/*`。  
- 须二选一：`--dry-run` / `--confirm`。  
- 输出 TSV 风格行：`visitorId kind before after added sessionDir`。

## 风险与回滚

| 风险 | 缓解 |
|------|------|
| 锁文件残留导致卡死 | 进程退出尽量 unlink；超时重试；运维可删 `.lock` |
| repair 标题不准 | 仅用首条 user；可手动改 meta（无 UI） |
| 多实例 NFS 锁语义 | 文档注明：同机/本地盘为主；跨机共享 dataDir 属进阶 |
| 越权已合入代码与契约不符 | 同意后对齐；不同意则按契约回滚相关 diff |

回滚：恢复无锁 `writeFile` 路径并移除 CLI（不推荐）；或仅禁用 CLI、保留锁。

## 测试要点

1. 并发 20 次对同一 meta「读 n → n+1 写」→ 最终 n=20。  
2. meta 仅 1 条、2 个 jsonl → dry-run `added=1` 且文件未变 → confirm 后 `sessions.length=2`。  
3. chat 两轮仍续写同一 jsonl；历史列表可切换。  
4. CLI 无 `--dry-run/--confirm` → exit 2。
