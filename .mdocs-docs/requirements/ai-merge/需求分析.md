# ai-merge — 需求分析

> 一句话：在行级三路 merge 审阅页，把**完整 git 冲突 Markdown**交给 AI，拿回**去掉冲突标记的定稿 Markdown**；不写发布说明、不直接 PUT。

## 背景

冲突 Merge 已有人肉「接收 / 拒绝 / 全部用我的/别人的」（见 `merge-inline-ui`）。冲突多或左右差异大时点选成本高。此前讨论确认：**不**用 Agent session / function calling；用短调用 `completeSimple`，与 `suggest-commit-message` 同族。

与 **merge-message**（合并完成后的发布说明 AI）分工明确：本需求只做流水线第 ① 步（填 resolution → 得到 merged），第 ② 步见 `publish-commit-message` 的 merge 增量。

**Agent / CLI（增量）**：Agent 暴露两个 tool（merge + merge-message）；CLI 一条 `ai-merge` 命令内部连调两次 HTTP。都不写库。

## 目标

1. Merge 页 **「AI 合并」**：`MergeSegment[]` → 完整 git 冲突 md → API → 定稿 md 写入编辑区。
2. 输入含**无冲突原文** + `<<<<<<< local` / `=======` / `>>>>>>> remote`（可选 `||||||| base`）；输出**不得**再含这些标记。
3. 能力受 **file-type-policy** / `canAiMerge`（本期 **md / html**）。
4. 失败可恢复：LLM/无模型/仍含标记 → toast，保留人手点选。

## 非目标（本期不做）

- AI 直接吐合完后的全文写回（易改非冲突区）；若将来做须校验 unchanged 指纹。
- function calling / 开 Agent 会话。
- AI 顺带生成 commit message（那是 merge-message）。
- sheet / graph 等 `whole-document` / `none` 管道。
- 改 diff3 / `buildThreeWayMergePlan` 算法本身。

## 验收标准

- [ ] md（及 html）Merge 页可见 AI 合并入口；sheet 整表页无此入口。
- [ ] 成功后冲突 pill 反映已决议段；用户仍可改单段接收/拒绝。
- [ ] 无模型配置或 LLM 失败：明确错误，segments 不被清空。
- [ ] 弹「发布说明」等 App 重渲染时，已填决议不被加载 effect 打回（既有 onError 依赖问题须保持修复）。
