# 删除文章可恢复 — 设计契约

> **状态**：已同意（2026-10-20）  
> 列表 `GET /documents/deleted` **一期一起做**。

## 方案摘要

| 项 | 约定 |
|----|------|
| 存储 | **不改表**；删文审计 `metadata_json` 增加 `recovery` 对象 |
| 正文来源 | 删前 head 的 `contentHash` + `blobRef`；依赖磁盘 `files/commits/` **本就不随删文清理** |
| 历史 | 只保住 **head**；不把整棵 commit DAG 塞进审计 |
| 恢复 | `restoreDocumentFromAudit({ actorVisitorId, auditId })`：同 `documentId` 重建行 + 工作区文件 + 单条 head commit |
| 权限 | 仅 **原 owner**（`recovery.ownerVisitorId === actor`）可恢复 |
| 冲突 | 同 `documentId` 已存在，或同域 `relative_path` 被占用 → `409` |
| UI | 本期 **不做**；审计仍无界面 |

## 删除 metadata 形状

`document.delete`（含 `viaFolderDelete: true`）在原有字段外增加 `recovery`：

```json
{
  "relativePath": "notes/a.md",
  "viaFolderDelete": false,
  "recovery": {
    "domainId": "…",
    "displayName": "a.md",
    "fileType": "md",
    "permission": 1,
    "parentId": null,
    "ownerVisitorId": "…",
    "createdBy": "…",
    "contentHash": "sha256…",
    "headCommitId": "uuid…",
    "blobRef": "ab/cdef…64hex…",
    "createdAt": "ISO",
    "updatedAt": "ISO"
  }
}
```

| 说明 | |
|------|--|
| 写入时机 | 在 `deleteDocument` **之前**读齐 `documents` 行 + `findCommitById(head)` 取 `blob_ref` |
| 无 head / 无 commit 行 | `recovery` 仍写文档元数据；`headCommitId`/`blobRef` 可为 `null`；恢复时若无 blob 则失败（或仅恢复空壳——**定稿：失败** `BLOB_MISSING`） |
| `folder.delete`（目录节点本身） | 可写精简 `recovery`（无 blob，`fileType: "dir"`）；恢复目录树 **本期不做**（只保证文件型 `document.delete` 可恢复） |
| `dir` / 无盘文件类型 | 同：无 blob 则本期不可 `restore` 正文类 API |

## 恢复流程

1. 读 `audit_logs` by `auditId`；要求 `action === "document.delete"` 且 `metadata.recovery` 存在。
2. 校验 `actorVisitorId === recovery.ownerVisitorId`。
3. 校验 `target_id`（原 documentId）不存在；`domainId + relativePath` 未被占用。
4. `readCommitBlob(recovery.blobRef)`；校验 hash 与 `contentHash` 一致（可选但建议）。
5. 事务：
   - `insertDocument`（**沿用原 documentId** 与 recovery 字段）
   - `insertCommit`（**沿用原 headCommitId**，同一 blobRef）
   - `insertAuditLog` `document.restore`（metadata：`auditId`, `relativePath`, `headCommitId`）
6. 事务外：`writeDocument(domainId, relativePath, content)`；`scheduleFtsIfNeeded`；图谱按 fileType 调度。

路径被占时 **不自动改名**（避免 silently 偏离用户预期）；调用方先处理冲突。

## API（拟）

| 方法 | 路径 | 说明 |
|------|------|------|
| `POST` | `/api/documents/restore` | body: `{ auditId: number }` → 返回文档 detail（同 create/get） |

列表「我删过的」可后做；本期调用方用 SQL / 未来列表 API 找 `auditId`。若要同期加：

| `GET` | `/api/documents/deleted` | 当前访客作为 actor 的最近 N 条带 `recovery` 的 `document.delete`（默认 50） |

**定稿倾向**：恢复 API **必做**；列表 API **建议同期做**（否则只有查库才能拿到 auditId）。请确认。

## 风险与回滚

| 风险 | 处理 |
|------|------|
| blob 已被人工删 / 磁盘坏 | `BLOB_MISSING`；审计仍保留线索 |
| 恢复后 DAG 只剩一点 | 文档写明；完整历史不在本期 |
| 同 path 新文已占用 | 409；不覆盖 |
| 旧删除无 recovery | 不可恢复；不假装能救 |
| metadata 变大 | 仅 head 指针，无正文拷贝进审计 |

## 测试要点

- 创建并发布 → 删 → 审计含 `recovery.blobRef` → restore → get 正文与删前一致，documentId 不变
- path 已被新文档占用 → restore 409
- 他人 auditId → 403
- 文件夹删除下的子文档审计亦含 `recovery`，可单独 restore 一篇
