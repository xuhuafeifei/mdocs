# Agent 上下文 LLM 压缩 — 需求分析

> 一句话：用量 ≥ 85% 时用访客模型做会话摘要压缩；压缩中前端展示状态，并锁定该 session 禁止并发读写。

## 背景

Session 会持久化 `get_document` / `web_*` 全文与多轮对话，长聊后 context 顶满。已有写后短提示，但**没有**跨轮压缩。用户明确要 **LLM 摘要**（不要只做硬裁剪），阈值 **85%**，过程中 **UI 提示 + session 锁定**。

## 目标

1. 开聊 / 开跑前估算用量；`percent >= 85` 则先压缩再跑（或压缩完成后再接受本轮用户消息进入模型）。
2. 用当前访客 Agent 配置的模型生成摘要，替换「中间历史」，保留最近若干轮原文。
3. 压缩期间：SSE/状态告知前端「正在压缩」；该 `sessionId` **锁定**，其它请求不得 append / 开第二路 run。
4. 压缩失败可恢复：不丢原文（先备份或写失败则回滚）。
5. **主动压缩**：用户可随时触发（不要求已到 85%）。

## 非目标（本期不做）

- 不压缩 system prompt / tools schema（只压 session 消息）
- 不做跨 session 全局压缩
- 不把摘要当成可编辑聊天气泡强加给用户编辑（可在时间线显示一条系统提示）

## 验收标准

- [ ] 人造长 session 使估算 ≥ 85% → 发下一条触发压缩 → 用量明显下降
- [ ] 压缩中前端可见「正在压缩上下文」类状态
- [ ] 压缩中对该 session 的第二路 chat / append → 拒绝或排队到结束后（契约定一种）
- [ ] 失败不截断为空白会话；jsonl 可恢复
- [ ] 单测：阈值判定、锁互斥、摘要写入形态

## 依据

- `context-usage.ts`：粗估 percent
- `session-meta-lock.ts` / `runSerialized`：已有 meta 串行
- 待确认：压缩中第二请求是 **409 立刻失败** 还是 **排队等待**（默认 **409 SESSION_COMPACTING**）
