# 冲突强制覆盖（owner）— 需求分析

> 一句话：发布遇版本冲突时，**文章所有者**可选择「用我的正文强制覆盖」；实现上走 **merge 发布通道**，最终工作区正文 = 本地稿，远端改动不进正文但进入 commit 图。  
> 状态：**已同意**（2026-09-15）

## 背景

多人编辑同一文档时，线性发布会因乐观锁失败得到 `409 VERSION_CONFLICT`，现网引导进 Merge 审阅。所有者有时明确要「别管远端，就以我这份为准」，需要一条比「进 Merge → 全部用我的」更短的路径，且 **非所有者不可用**。

上传附件在 merge 端语法展示问题本期 **不管**。

## 冲突判定（与现网对齐）

线性发布前服务端比较：

- 客户端带来的 **`localBaseCommitId`**（开编分叉点 / 草稿冻结的 base）
- 服务端当前 **`documents.head_commit_id`**（远端 tip，`remoteCommitId`）

**不一致 → 冲突（409）**。一致则可线性推进。

举证：[`archive/commit-naming-and-merge-base.md`](../../archive/commit-naming-and-merge-base.md)；`document.service.ts` → `assertNoVersionConflict`。

## 目标

1. 冲突入口（如 `ConflictModal` / 等价 UI）在「去合并」之外，对 **文档 owner** 增加 **强制覆盖** 选项。
2. 非 owner（含 PUBLIC_EDIT / 邀请编辑）**看不到或点了 403**。
3. 强制覆盖成功后：工作区正文 = **本地草稿/本地快照**；head 前进；历史仍可追溯（见设计契约）。
4. 不改变「普通人走 Merge 审阅」的主路径。

## 非目标

- 改三路 diff 算法 / merge-inline UI 行为（「全部用我的」可继续存在，与本入口不同）
- 上传文件 / 附件在 Merge 预览里的语法高亮
- 非 owner 的强制覆盖、域管理员代覆写
- CLI / Ask `overwrite_document` 与本冲突强制覆盖混为一谈（Ask 覆写是另一条线性路径）

## 验收（草案）

- [ ] owner 在 409 后可见「强制覆盖」；确认后正文为本地稿，head 更新。
- [ ] 非 owner 无此按钮；若绕过 API 调用 → 403。
- [ ] 覆盖过程中若 head 再次被推进 → 仍 409（不静默盖掉更新的 tip）。
- [ ] md / html 均可用（按各自 `contentKind` / raw 管道落盘）。
