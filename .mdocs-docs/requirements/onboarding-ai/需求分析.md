# onboarding-ai — 需求分析

> 一句话：项目早期引入 **仅用于上手 mdocs 的 Agent**，**不具备任何辅助编写能力**；Agent 落在 mdocs，lobe 本期不参与写作类能力。

## 背景

- 产品早期，用户对「域 / 草稿 / 发布 / Slash / Markdown 快捷键」等成本高，希望有人「带着用」。
- 此前讨论过块级润色、选区插入等写作向 AI；本期**主动收缩范围**，先只做上手，避免一上来做编辑器修订 UI 与写回链路。
- 架构原则已对齐：**Agent 在 mdocs；lobe 只提供底层编辑能力**（本期上手 Agent **不依赖** lobe 块级写回 API）。

## 怎么看待「只上手、不辅助编写」（立场）

**可行，且适合当早期护栏**——前提是产品上把「不会写」做成清晰能力边界，而不是半残写作助手。

| 好处 | 风险 |
|------|------|
| 范围小：不碰选区写回、块级 diff、Accept/Reject | 用户一开口「帮我改这段」就会撞墙，拒绝话术要设计好 |
| 先把 Agent 壳（入口、会话、鉴权、开关）跑通 | 若上手内容用静态 FAQ 就够，上模型可能过重 |
| 与后续「写作 Agent」可并存：同一壳，不同工具权限 | 「只会聊天不会改文档」容易被当成半吊子，期望管理很重要 |
| 不强迫本期改 lobe | 上手若强依赖「在编辑器里演示插入」，以后仍可能要 lobe 只读高亮/引导 API |

**建议的产品定义（本期）：**

- Agent = **产品向导 / 答疑**（怎么建域、怎么发布、草稿是什么、为何发布后视口曾跳动等）
- Agent ≠ 作者（不生成正文、不润色、不改 Lexical、不替用户点发布——除非明确做成「引导用户自己点」的逐步说明）

若验收上仍觉得「不能改文档就没用」，应改回非目标谈判，而不是偷偷加半套写作能力。

## 目标

1. 新用户（或久未使用的用户）能通过 Agent **更快理解 mdocs 核心工作流**（打开文档、编辑、草稿、发布、权限/域的基本概念）。
2. Agent **明确拒绝**一切「代写 / 润色 / 按选区改文档 / 插入正文」类请求，并引导用户用 Slash、发布按钮等自助完成。
3. 实现位置在 **mdocs**；不把模型调用、prompt、密钥放进 lobe。

## 非目标（本期不做）

- 辅助编写：润色、续写、大纲生成、翻译正文、按选区改写
- 操作底层编辑器数据：块级替换、插入节点、`setDocument` 由 Agent 触发写回
- VS Code 式 Accept/Reject 修订 UI
- lobe 内置 AI 或 onboarding 聊天壳
- 多 Agent / 自动改仓库代码 / CLI 代操作（与「上手 mdocs 产品」无关）

## 验收标准

1. 有稳定入口（例如设置旁、空文档欢迎区或侧栏）可打开上手 Agent。
2. 对「如何发布 / 草稿是什么 / 如何插入代码块」等预设问题类询问，能给出**可执行的产品内指引**（指向 UI 位置或简短步骤）。
3. 对「帮我把这段写得专业一点 / 在第三段插入……」类请求：**不修改文档**，并说明本期仅支持上手答疑。
4. 关闭开关或未配置模型时，产品可降级（隐藏入口或提示不可用），不影响编辑/发布主路径。
5. 不引入 lobe 发版依赖（本期）。

## 知识与双仓库（mdocs-site ↔ mdocs）

**立场：`mdocs-site` = 人读手册真源；mdocs Agent = 通过 Skill 读同一套知识的机器视图。不要让人在两个仓库各维护一份正文。**

### 分发模型：打包进 mdocs（默认），不做 site 推送 / 不做百台拉取

site **不知道**有哪些 mdocs 实例——推送不可行；百台运行时去拉固定 URL 也不划算。默认：

1. **发版 CI**：从 `mdocs-site/docs/docs/**` 生成 skill 包，打进 `@fgbg/mdocs`（版本与 mdocs 对齐）。  
2. **各实例**：`npm i` / 安装即自带同版知识；Agent 读本地 skills。  
3. **运行时拉取**：后期可选（不升 mdocs 只更新手册时再考虑），**非默认**。

| 策略 | 做法 | 本期态度 |
|------|------|----------|
| **随 mdocs npm 打进包内** | 安装即有默认知识 | **采用（默认）** |
| 运行时从固定 URL 拉取 | 百台各自拉中心地址 | **不做默认**；后期可选 |
| site 推送到各实例 | site 要知道「分发给谁」 | **不做** |
| 启动时顺带跑 mdocs-site | 每实例多进程/端口 | **不为 Agent 做** |
| 仓库内手拷贝两份给人改 | 双源漂移 | **反对** |

### 打包进 mdocs 后，数据如何变成 Skill（倾向）

不必在运行时「再发明一层 site」。发版时做一次转换即可：

```
mdocs-site/docs/docs/**/*.md     ← 人改真源
        │  CI / mdocs release 脚本
        ▼
skills/
  drafts/SKILL.md          ← 可由 drafts.md + 元数据生成或薄包装
  domain/SKILL.md
  index.json               ← 标题/路径/关键词，供 list + 粗检索
        │
        ▼
打进 @fgbg/mdocs 包（如 dist/agent-skills/ 或 files 字段纳入）
        │  安装/启动
        ▼
数据目录可先拷一份默认 skills；Agent：list / search_index / read_skill
```

生成策略可渐进：

1. **早期**：一页 site 文档 ↔ 一个 skill 目录（或一组相关页合并成一个 skill）；`SKILL.md` = 标题 + 正文（或摘要）+ 可选 `keywords` frontmatter。  
2. **检索**：对打包内的 `index.json` / 正文做**本地关键词检索**（mdocs 已有 jieba/FTS 经验，可复用思路，但索引的是 skills 不是用户文档）。  
3. **不必**为了 Agent 去复用 Rspress 浏览器端搜索 UI。

### 能否复用 mdocs-site「关键词检索」？

site 侧检索实质是 **Rspress 静态站本地搜索**（主题内建索引 + `theme/search-hooks.ts` 只修 link 的 `withBase`），绑在文档站前端，**不是**可给 mdocs 服务端直接 `import` 的库。

mdocs 自己的 `search.service` / FTS5 是给**用户知识库文档**用的，权限模型也不同。

| 复用什么 | 建议 |
|----------|------|
| site 的 Markdown 正文 | ✅ 打包真源 |
| Rspress 搜索组件/索引格式 | ❌ 不直接复用 |
| 「关键词检索」产品能力 | ✅ 在 mdocs 内对 **skills 包**自建轻量索引（或简单扫文件） |

### 启动 mdocs 时顺便跑起 mdocs-site？

**不推荐作为 Agent 知识路径的主方案。**

| | 顺带跑 site | 打包 skills |
|--|-------------|-------------|
| 进程/端口 | 多一个 Rspress/静态服务 | 无 |
| 100 台部署 | 每台多一套站点栈 | 只多静态文件 |
| Agent 读知识 | HTTP 爬自己或 localhost 文档站，绕 | 本地读文件 |
| 人读手册 | 有完整站点体验 | 可另外部署公网站点；产品内可用「打开文档链接」指到公网 site 或内嵌静态页（后期） |

若目标是「给用户看漂亮文档站」：公网/内网**单独部署一份** mdocs-site 即可，与 Agent 知识包解耦。  
若目标是「Agent 会用手册」：**打包 skills 足够**，无需每个 mdocs 实例再挂一个 site。

## 密钥层级（愿景 vs 本期）

**愿景（记入需求，不本期实现）：**

- 本质是「**这份 Model 配置的授权范围**」，不是多模型市场，也不是把 apiKey 复制给别人。
- 路径：个体自用 → **配置授权（使用权）** → 团队 / 更开放。
- 授权语义：所有者保存一份 model + apiKey；被授权人看到的是「可用配置」（谁共享的 + 模型名），**永远看不到 key**；chat 时服务端用所有者存的 key 调模型。
- 用量监控：个人自用可看 DeepSeek 控制台；**一旦共享，用量才刚需**（按配置 + 调用者记 token），与授权同期考虑。

**本期（2026-07-27 增量）：**

- 只接 **DeepSeek**；每人在设置页保存**自己的一份**配置（模型二选一 + apiKey），写入 SQLite。
- **不做**配置授权、邀请、别人可用列表、token 用量 UI。
- 未配置 key 时 Agent 入口 / chat 降级，主编辑路径不受影响。

## 本次变更（2026-07-27）— 个人 Model 配置

> 一句话：把手动 env 配 key，改成「当前访客在设置里保存自己的 DeepSeek 配置」。

| 做 | 不做 |
|----|------|
| SQLite：配置 `id` + `name` + model + apiKey；一人一份 | 配置授权 / 「可用配置」列表 |
| 设置页：名称（可选）、模型二选一、apiKey | 自定义 endpoint、多 provider |
| 未填名称 → `{访客昵称}的 ds 配置` | token 用量监控 |
| GET/PUT `/api/agent/config`；status/chat 读本人配置 | 一人多条配置（表已预留 id） |
| GET 脱敏或不回传明文 key | — |

验收补充：

1. 访客 A 保存配置后，status.enabled=true，可 chat。  
2. 访客 B 无配置 → enabled=false；看不到 A 的 key。  
3. 更新模型时可省略 apiKey 保留旧值；空串拒绝。
