# 异步任务队列 — 设计契约

> **状态**：已同意（2025-01-15）
> 代码已实现。

## 方案摘要

构建 `TaskQueue` 单例（`src/server/task-queue/`），**单队列 + 并发数**模型：一条队列按顺序排，前 N 个在跑（N = concurrency），后面的排队。任务通过 `TaskContext` 与调度器交互：`emit()` 上报结构化事件，`yield()` 主动让出时间片（移到队尾挂起）。进度日志以 JSON Lines 写入文件，前端轮询查询状态。

图谱生成任务接入此框架，每处理完一小批文档后主动 yield，让小任务有机会插队。

src/server/task-queue/

## 核心类型

### TaskScheduler（调度协作接口，任务视角）

任务通过这个接口与调度器交互，职责单一：**让出资源**。

```typescript
interface TaskScheduler {
  /** 询问调度器：我该让出了吗？
   *  满足两个条件返回 true：
   *  1. 队列长度 > concurrency（有人在排队）
   *  2. 当前任务已连续运行超过 timeSliceMs
   */
  shouldYield(): boolean;

  /** 主动让出时间片。
   *  任务 state 改为 suspended，移到队尾，返回 pending Promise。
   *  等任务重新排到前 concurrency 位置时，Promise resolve，任务从这里继续。
   */
  yield(): Promise<void>;
}
```



### GraphLifecycle（事件上报接口，图谱任务专用）

具名方法，类型安全。内部实现会转成 `emit(event, data)` 写入日志。

```typescript
interface GraphLifecycle {
  taskStarted(data: { targetType: string; targetId: string; totalDocs: number }): void;
  docStarted(data: { docPath: string; docId: string; index: number; total: number }): void;
  docCompleted(data: { docPath: string; docId: string; conceptsExtracted: number; durationMs: number }): void;
  docFailed(data: { docPath: string; docId: string; error: string }): void;
  folderStarted(data: { folderPath: string; folderId: string; docCount: number }): void;
  folderCompleted(data: { folderPath: string; folderId: string; durationMs: number }): void;
  domainStarted(data: { domainId: string; folderCount: number }): void;
  domainCompleted(data: { domainId: string; totalNodes: number; totalEdges: number; durationMs: number }): void;
  taskCompleted(data: { totalDocs: number; nodes: number; edges: number; durationMs: number }): void;
  taskFailed(data: { error: string; durationMs: number }): void;
  taskYielded(data: { current: number; total: number; reason: string }): void;
}
```



### TaskContext（内部通用接口，框架视角）

框架内部使用的通用上下文，把事件上报 + 调度协作合在一起。具体任务（如图谱）不直接用这个，而是用上面的具名接口。

```typescript
interface TaskContext {
  readonly taskId: string;

  /** 通用事件上报（GraphLifecycle 等具名接口内部会调用这个） */
  emit(event: string, data?: any, level?: 'info' | 'warn' | 'error'): void;

  /** 调度协作 */
  scheduler: TaskScheduler;
}
```



### Task（调度器视角的任务）

```typescript
interface BackgroundTask {
  id: string;                    // 任务 ID = 任务类型的 dedupKey，同一目标唯一
  type: string;                  // 任务类型，如 'graph-generate'
  payload: Record<string, any>;  // 任务参数
  state: 'queued' | 'running' | 'suspended' | 'completed' | 'failed';
  createdAt: number;
  startedAt?: number;
  finishedAt?: number;
  error?: string;
  lastRunAt?: number;            // 最近一次开始/恢复运行的时间（用于时间片判断）

  // 运行时
  run?: (payload: any, ctx: TaskContext) => Promise<void>;
  resume?: () => void;           // yield 挂起后恢复的回调（resolve 那个 Promise）
}
```

> 注 1：任务在队列中的**位置决定了它是 "running" 还是 "pending"**——索引 < concurrency 就是在跑（或应该被跑），索引 >= concurrency 就是在排队。`state` 字段区分的是"正在执行"还是"挂起等待 resume"。
>
> 注 2：**taskId = dedupKey**，同一目标（如同一篇文档）全局只有一个任务，重复触发命中去重。重新生成时直接复用同一个 ID，日志文件覆盖。前端刷新后可直接通过目标信息拼接 ID 查询。



### TaskQueue（对外公共 API）

```typescript
interface TaskQueue {
  /** 注册任务类型
   *  @param type 任务类型名，如 'graph-generate'
   *  @param def 任务定义：makeId + run
   */
  registerTask<P>(type: string, def: TaskDefinition<P>): void;

  /** 入队一个任务
   *  @returns 任务信息（可能命中去重）
   */
  enqueue(type: string, payload: any): EnqueueResult;

  /** 查询任务状态 + 日志 */
  getTask(taskId: string): TaskStatusResult;

  /** 配置：并发数 */
  concurrency: number;

  /** 配置：时间片（毫秒） */
  timeSliceMs: number;
}

interface TaskDefinition<P> {
  /** 根据 payload 生成任务 ID（同时也是去重键） */
  makeId: (payload: P) => string;
  /** 任务执行函数，接收生命周期 + 调度器 */
  run: (payload: P, lifecycle: any, scheduler: TaskScheduler) => Promise<void>;
}

interface EnqueueResult {
  taskId: string;
  status: 'pending' | 'running' | 'completed';
  position: number;   // 0 = 正在跑
  deduped: boolean;   // 是否命中去重
}
```



### LogEntry（日志行结构）

```typescript
interface LogEntry {
  ts: string;       // ISO 时间戳
  event: string;    // 事件名，点分层级，如 'doc.completed'
  data?: any;       // 事件数据
  level?: 'info' | 'warn' | 'error';  // 默认 info
}
```

## 调度策略



### 单队列 + 并发数

- **只有一条队列**，所有任务按顺序排列
- `concurrency` 可配置，默认 **2**
- 队列中**前 concurrency 个位置**的任务是"活跃"的（应该在跑）
- 后面位置的任务是"排队"的，等前面有空位才顶上
- 所有任务类型共享同一资源池（瓶颈是 agent API 额度）

```
队列：[任务0, 任务1, 任务2, 任务3, 任务4, 任务5]
       └─ concurrency=2，前 2 个活跃 ─┘  └── 排队 ──┘
```



### 入队去重

- 每种任务类型定义自己的 `makeTaskId(payload) → string` 函数，生成的 ID 即去重键
- 入队时检查整条队列中是否已有相同 ID 且未完成的任务
- 有则直接返回该任务（标记 `deduped: true`）
- 无则创建新任务（ID = makeTaskId(payload)），塞到队尾，触发调度
- 同一目标重新触发：如果已有 completed/failed 的任务，**覆盖重新入队**（先移除旧的再加新的，日志文件重新开始写）



### 调度（schedule）

调度器只做一件事：**让前 concurrency 个位置上的任务都处于运行状态。**

每次调度检查前 N 个任务：

- 如果是 `queued`（还没开始过）→ 启动它，调 `task.run()`
- 如果是 `suspended`（yield 挂起了）→ 恢复它，调 `task.resume()`
- 如果是 `running` → 不用管，它自己在跑
- 如果是 `completed` / `failed` → 从队列中移除，后面的往前顶

调度时机（任何变化后都会触发）：

- 新任务入队
- 任务完成 / 失败
- 任务 yield



### 协作式时间分片（yield）

- 任务在循环中定期调用 `ctx.shouldYield()`
- 调度器根据以下条件判断是否该 yield：
  1. **队列长度 > concurrency**（有人在排队，让出才有意义）
  2. **当前任务连续运行超过** `timeSliceMs`（默认 30s）
- 两个条件都满足，`shouldYield()` 返回 true
- 任务调用 `ctx.yield()` 后：
  1. emit 一条 `task.yielded` 事件
  2. 创建 pending Promise，把 resume 存到任务上
  3. 任务 state 改为 `suspended`
  4. **把任务移到队尾**
  5. 触发调度（前面空位会被后面的任务顶上）
  6. 返回 Promise，任务 await 挂起
- 等这个任务又排到前 concurrency 个位置时，调度器调用 `resume()`，任务从 yield 处继续

```
初始（concurrency=2）：
  [A跑, B跑, C等, D等, E等]

A yield → A 移到队尾，state=suspended：
  [B跑, C跑, D等, E等, A挂]
   ↑ 调度发现 C 是 queued，启动它

B 跑完 → B 移除，后面顶上：
  [C跑, D跑, E等, A挂]
   ↑ 调度发现 D 是 queued，启动它

A 排到前 2 了 → 调度发现 A 是 suspended，resume：
  [C跑, A跑, ...]
   ↑ A 从 yield 的地方继续
```



### 状态查询

查询接口返回状态时的判定顺序：

1. 隐藏文件存在 → `completed`（真相源）
2. 任务在队列中：
  - state = `completed` / `failed` → 对应状态
  - 索引 < concurrency → `running`
  - 索引 >= concurrency → `pending`
  - 附带 `position`（排队位置，0 表示正在跑）
3. 任务不在队列中（重启后）：
  - 日志文件存在，最后一条是 `task.completed` → `completed`
  - 日志文件存在，最后一条是 `task.failed` → `failed`
  - 日志文件存在，mtime > 5 分钟 → `stale`（超时/中断）
  - 日志文件存在，mtime ≤ 5 分钟 → `stale`（重启中断）
  - 日志不存在 → `not_found`



## 日志存储

- 目录：`~/.mdocs/task-logs/{taskId}.log`
- 文件名 = taskId（即去重键），同一目标永远同一个文件
- 格式：JSON Lines，每行一个 LogEntry
- 写入：任务开始时清空文件（重新生成覆盖旧日志），之后追加写
- 查询：读取最后 N 条（默认 50 条），从文件尾部往前读
- 清理：第一版不做自动清理，未来心跳机制处理

```typescript

  docCompleted(data: { docPath: string; docId: string; conceptsExtracted: number; durationMs: number }): void;
  docFailed(data: { docPath: string; docId: string; error: string }): void;
  folderStarted(data: { folderPath: string; folderId: string; docCount: number }): void;
  folderCompleted(data: { folderPath: string; folderId: string; durationMs: number }): void;
  domainStarted(data: { domainId: string; folderCount: number }): void;
  domainCompleted(data: { domainId: string; totalNodes: number; totalEdges: number; durationMs: number }): void;

```

实现上，`GraphLifecycleImpl` 内部把每个具名方法转成 `ctx.emit(eventName, data)`，调用通用 emit。

### 调度能力独立

任务函数接收两个独立参数，职责分离：

```typescript
async function generateGraph(
  payload: GraphGeneratePayload,
  lifecycle: GraphLifecycle,  // 事件上报
  scheduler: TaskScheduler,   // 调度协作（shouldYield / yield）
): Promise<void>
```



### 改造步骤

1. 从 `graph.service.ts` 中提取 `generateGraph()` 主逻辑
2. 改为接收 `GraphLifecycle` + `TaskScheduler` 两个参数
3. 所有进度输出改为调用 `lifecycle.xxx()` 具名方法
4. 每处理完 5 篇文档调用一次 `scheduler.shouldYield()`，是则 `await scheduler.yield()`
5. 注册任务类型 `graph-generate` 到 TaskQueue
6. 接口改为调用 `taskQueue.enqueue('graph-generate', payload)`，返回 taskId

## 风险与回滚

- **风险**：yield 逻辑可能引入 bug，导致任务挂起或重复执行。
  - 缓解：第一版 yield 触发条件保守（只有等待队列非空时才触发），可配置开关
- **风险**：服务重启后任务丢失，用户体验断裂。
  - 缓解：查询接口靠日志文件 + 隐藏文件判定状态，不会"查不到"；用户可手动重新触发
- **回滚**：关掉并发控制（concurrency = 999）即退化为无队列模式；必要时回退到同步接口



## 测试要点

1. 单任务入队、执行、完成，状态流转正确
2. 多任务入队，并发数不超过 concurrency，按顺序执行
3. 同目标重复入队，命中去重
4. 大任务运行中，新任务入队，大任务在 yield 点让出，新任务执行
5. 任务失败，状态正确，错误信息记录
6. 日志写入正确，查询返回最后 N 条
7. 服务重启后，查询历史任务状态正确（靠日志 + 隐藏文件）
8. 隐藏文件存在但队列中无任务，查询返回 completed
