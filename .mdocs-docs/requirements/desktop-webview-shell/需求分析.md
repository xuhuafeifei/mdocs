# desktop-webview-shell — 需求分析

> 一句话：做一个可安装的桌面壳，点图标打开自己的 mdocs，不必每次在浏览器里敲网址。  
> 状态：**已同意**（2026-09-13）

## 背景

Android 壳已落地：填服务器地址 → 系统 WebView 打开该站；无自绘顶栏；剪贴板同源文档链接可跳转。桌面同样痛点。

mdocs 仍是自托管 Web。壳不重做编辑器。前端 API 走相对路径 `/api`，必须整页加载用户填写的源站。

用户要求 **macOS 与 Windows 都支持**（不上架）。

## 目标

1. 可安装的桌面应用（不上架、不进 npm）
2. 交互对齐 Android：首次填 URL → 之后直达；可更换服务器
3. **不要**再做一条常驻应用顶栏；系统窗口按钮保留即可
4. 焦点回到窗口时：剪贴板若为**已配置源站**且含 `/doc/<id>` 或 `#/doc/<id>`，打开该文
5. 上传 / 下载尽量接近桌面浏览器
6. 一套源码覆盖 **macOS + Windows**

## 非目标（本期不做）

- Linux、应用商店、自动更新、托盘、多窗口工作区
- 把前端打进安装包 / 改 API 绝对地址
- 原生重写编辑器、身份
- 和 Android 共用一份二进制（只对齐行为）
- 解决 ICP 备案拦截（那是域名/云厂商，不是壳）
- 在 Mac 上交叉编译出 Windows 安装包（Windows 包在 Windows 本机或 CI 编）

## 验收标准

1. 未保存地址 → 填写页；非法 URL 拒绝
2. 重启后仍打开同一地址
3. 能注册访客、打开并编辑文档（取决于该服务器）
4. 复制本站文档链接后切回窗口 → 打开该文；其它站链接忽略
5. 主色对齐 `--mdocs-accent`（`#4CAF50`），图标用 `mdocs-logo`
6. 同一 `desktop/` 工程在 macOS 与 Windows 上都能编出可运行安装包

## 依据

- 路由：`HashRouter`，规范 `http://host/#/doc/<id>`（`src/web/main.tsx`）
- 平台决议：2026-09-13 用户要求 Mac + Windows → [设计契约](./设计契约.md) 选用 Tauri 2
